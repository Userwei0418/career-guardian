# 职护 Career Guardian

职护是一套面向应届生和入职 0～3 年职场新人的个人职业守护系统。

它不替用户找工作、做选择、签合同、记账或规划人生，而是在职业生涯的关键节点守住五件容易因信息差、时间压力和情绪而失真的事：**机会是否真实，选择是否清醒，承诺是否一致，钱是否对得上，经历是否留下价值。**

> 把分散、模糊、容易遗忘的职业信息，变成可核对的事实、可理解的影响、可追踪的行动和可复盘的结果。

## 产品为什么这样设计

职业问题很少只发生在一个页面里。一条岗位信息会变成目标和准备；外部拿到的 Offer 会变成选择；接受后的书面合同需要核对；入职后的工资和支出需要验证；真实工作又会沉淀为能力、作品和下一次选择的筹码。

因此，职护不是五个彼此独立的小工具，而是一条连续的职业证据链：

```text
市场与岗位
  → 机会守护：看清外部机会和个人差距
  → 决策守护：看清 Offer 条件、未知和取舍
  → 权益守护：核对合同、协议与此前承诺
  → 收支守护：核对工资、到账、支出和真实结余
  → 成长守护：把工作过程沉淀为证据、能力和未来方向
  └──────────────────────────────→ 回到新的机会与选择
```

`/today` 是这条旅程的全局驾驶舱：它只汇总五个守护当前最重要的状态和入口，不复制各模块的完整任务、原文、情绪或分析内容。

## 一套共同的守护方法

五个模块处理的材料不同，但都遵循同一套产品方法：

```text
原始材料或真实记录
  → 程序保存来源、时间、版本和权限
  → 确定性规则识别字段、冲突、金额和状态
  → AI 理解语义、解释影响并生成建议草稿
  → 用户核对、修正和确认
  → 形成正式事实、决定、行动或资产
  → 后续结果回写，供下一次核验和复盘
```

### 1. 先保留事实，再提供建议

- 原件、用户填写、程序计算、AI 推断和用户确认是不同层级，不能混写。
- 缺失值保持“未知”，不能为了让页面完整而补成 `0`、默认值或确定结论。
- 任何重要结论都应能回到来源、时间、版本和用户确认动作。

### 2. AI 是分析助手，不是事实所有者

- 程序负责权限、日期、金额、状态、版本、幂等、聚合和写入门禁。
- AI 负责长文理解、语义归类、影响分析、解释、草拟和提出待确认问题。
- 用户负责确认事实、作出选择以及决定是否对外发送、写入档案或跨模块复用。
- Agent 只能调用受控业务接口，不能获得任意 SQL 或绕过确认直接改库。

### 3. 一次输入，多处复用，但不静默流转

同一份 Offer、合同、工资条、会议纪要或作品可以服务多个守护，但跨模块流转前必须说明：发送到哪里、使用哪些内容、依据是什么、会产生什么影响。未经确认的候选不会被升级为正式事实。

### 4. 只在需要时展开复杂度

首屏先回答“现在最值得处理什么”，原文、计算过程、版本差异和低频工具按需打开。系统尽量让用户补一句、选一次或确认一个关键点，而不是强迫用户先填完整流程表。

### 5. 守护选择质量，不承诺结果

职护可以提示信息不足、条件冲突、风险、差距和下一步，但不承诺录用、不判断合同一定违法、不替用户决定是否接受 Offer，也不把 AI 分数包装成职业价值。

## 五大守护模块

| 模块 | 守住什么 | 主要守护维度 | 用户最终得到什么 |
| --- | --- | --- | --- |
| 机会守护 | 外部机会与个人准备之间的真实性 | 市场、岗位、匹配证据、目标、训练 | 可追溯的岗位事实、目标差距和准备路径 |
| 决策守护 | 选择过程的质量 | Offer 事实、收入与生活、个人底线、未知、时间 | 问得清、算得明、愿意承担且可回看的决定 |
| 权益守护 | 书面承诺及其实际影响 | 合同材料、关键条款、原文依据、承诺差异、版本 | 能定位原文的核对项、风险解释和审查记录 |
| 收支守护 | 真实发生的经济事实 | 收入、支出、到账、退款/报销/转账、趋势 | 不重复、不漏算、可解释的可信账本与异常线索 |
| 成长守护 | 工作经历能否转化为可带走的价值 | 当下工作、过去资产、未来方向 | 工作外脑、职业证据、能力筹码和客观里程碑 |

### 机会守护：看清市场，也看清自己

机会守护不是职位搬运站，也不把“匹配度”当作录用概率。它从四个维度守护用户：

- **市场维度**：用经过来源治理和质量门的岗位事实观察城市、职类、招聘类型、技能和薪资结构。
- **岗位维度**：保留岗位来源、正文、时效和数据质量，避免把残缺、重复或历史岗位描述成当前可靠机会。
- **个人维度**：只有在用户选定具体岗位并绑定本人简历后，才分析已有证据、门槛、差距和风险。
- **准备维度**：将目标岗位继续连接到能力路线、简历微调草稿、模拟面试和复盘。

守护方式是：`市场全景 → 方向下钻 → 岗位事实 → 简历证据对照 → 设为目标 → 准备与训练`。AI 解释证据和差距，统一规则维护匹配口径；微调内容始终是待确认草稿，不覆盖原简历。职护不参与真实招聘和真实投递。

### 决策守护：不替你选，但让选择有依据

决策守护守的是选择过程，而不是保证某个选择未来一定正确：

- **事实维度**：区分书面条件、口头表达、用户转述、系统估算、已确认和未知。
- **现实维度**：把薪资、奖金、城市成本、必要支出和储蓄目标放到同一口径下，观察保守、当前假设和条件兑现三种情景。
- **取舍维度**：记录必须满足、不能接受、可以交换的条件，以及继续求职、留在当前工作等现实替代。
- **沟通维度**：优先找出最可能改变决定的少数问题，生成 HR 确认和谈薪草稿，并保留实际回复。
- **时间与追溯维度**：管理回复期限、暂缓复盘和事实版本，在最终决定时冻结当时依据、未知和理由。

守护方式是：`录入 Offer → 核对事实与冲突 → 看三种情景 → 明确底线 → 问关键问题 → 比较或判断 → 记录决定及依据`。收入条件冲突时停止生成看似精确的结论；只有用户本人可以接受、拒绝或暂缓。

### 权益守护：让合同风险回到原文

权益守护是一套劳动者视角的合同审查工作台，不要求用户先录入 Offer，也不替代律师：

- **材料维度**：私有保存劳动合同、实习协议、竞业、保密、培训服务期、补充或离职协议。
- **条款维度**：识别岗位、工资、试用期、工时、社保公积金、竞业、违约责任等关键条件，未知保持未知。
- **影响维度**：以“优先关注、建议核对、一般提醒”解释条款对劳动者的现实影响，不制造安全总分。
- **证据维度**：每条结论绑定原文片段；完整原文只在用户主动查看时打开。
- **一致性维度**：用户主动关联 Offer 后，核对合同与此前承诺的结构化差异。

守护方式是：`上传或粘贴 → 本地解析与脱敏 → 确定性规则复核 + AI 分段解读 → 原文证据门禁 → 条款追问 → 保存审查快照`。模型只接收完成本地脱敏的必要条款；模型不可用时保留规则结果，不把 AI 判断写成确定法律结论。

### 收支守护：从识别流水到确认经济事实

收支守护不是单纯记账，也不是把工资条和消费账单分成两个孤岛。它从以下维度守护钱的真实变化：

- **收入维度**：核对工资构成、扣款、Offer—合同—工资条一致性以及是否真实到账。
- **支出维度**：识别账单和长截图，处理分类、商户、趋势及重叠截图带来的重复记录。
- **事实维度**：把工资条、银行、微信、支付宝等多来源观察归并为现实中实际发生的一次经济事实。
- **关系维度**：区分收入、支出、内部转账、退款、报销、拆分到账、多笔合并和信用卡还款，避免重复计算。
- **分析维度**：所有图表、月结、异常和 AI 问询只消费用户已经确认的账本事实。

守护方式是：`手工/文件/OCR/自然语言录入 → 形成候选 → 程序查重和匹配 → AI 解释疑难项 → 用户确认、合并、拆分或排除 → 可信账本 → 图表、月结与问询`。未确认候选绝不进入正式统计；工资条上的“实发”也不会自动冒充银行到账。

### 成长守护：把正在经历的事，变成未来带得走的筹码

成长守护不是打卡工具，也不是课程商城。它用三个平级的时间视角守护职业成长：

#### 当下的事：守住生存、效率和真实进展

用户可以在同一入口提交会议纪要、方案片段、聊天记录或零散进展，并手工填写客户/项目、发生时间和下次跟进。系统围绕用户确认的项目总目标组织长期工作线和推进节点。

这里的 Agent 不只是总结单份纪要，而是站在项目全局判断本次材料对项目总目标和具体工作线分别产生了什么作用：**推进、受挫、方向变化、补充上下文、暂时无变化，或证据不足。** 建议先保持 `suggested`，由用户确认后才改变正式进展、象限、可汇报状态或停滞时钟。

由此形成：`项目总目标 → 长期工作线 → 推进节点 → 多次材料 → 增量影响 → 人工确认 → 时间线、停滞提示、周/月回顾`。沟通、汇报、情绪脱敏、STAR 和周报都是围绕具体事项按需调用的能力，不强迫用户每一步填写表单。

#### 过去的果：守住证据、能力和职业资产

作品、上线链接、项目结果、客户反馈、反思和高价值事件按“**作品 → 证据 → 能力 → 筹码**”沉淀。AI 可以整理 STAR 维度、提取候选能力和提出反思问题，但能力只有在存在来源且经用户确认后才能成为正式事实；系统不直接替用户生成一份完整简历。

#### 未来的路：守住清醒、差距和行动方向

用户先确认目标岗位或目标层级，再把过去积累的能力证据与有来源、有时间窗口的市场信号对照，形成筹码、差距和里程碑。系统展示“还差什么”和证据是否充分，不输出“你应该跳槽”之类的主观决定。里程碑经用户确认后，才会反推回“当下的事”。

原始情绪默认保持私密；只有用户确认后的客观事实和行动，才允许进入周报、资产、能力分析或跨守护上下文。

## 跨模块如何形成闭环

职护以职业事件、证据、结论、行动、决定和结果作为共同语言：

| 上游事件 | 下游守护 | 只传递什么 |
| --- | --- | --- |
| 选定目标岗位 | 机会 → 成长 | 目标上下文、已确认差距和准备行动 |
| 外部获得 Offer | 机会/外部 → 决策 | Offer 原件、来源和用户确认的事实 |
| 接受 Offer | 决策 → 权益/收支/成长 | 决定依据与三项待核验入口，不预造合同、工资或入职事实 |
| 上传劳动合同 | 权益 ↔ 决策 | 用户主动关联后的承诺差异和原文证据 |
| 录入工资条与到账 | 收支 ↔ 权益/决策 | 已确认金额、扣款、到账和一致性结果 |
| 确认工作成果与能力 | 成长 → 机会 | 用户允许复用的证据、能力事实和作品摘要 |

跨模块默认只传摘要和结构化事实，不传完整原文、原始情绪或无关私人信息。每次正式写入都保留来源和撤销/版本记录。

## 产品中的几个支撑入口

- **今日总览 `/today`**：汇总职业阶段、五个守护的重要信号和下一入口；不承担各模块的详细工作。
- **个人中心 `/profile`**：管理简历版本、目标、Offer、合同、收入结果和个人材料，保留来源及版本关系。
- **知识 `/knowledge`**：根据当前问题提供相关知识，不以泛化文章打断主流程。
- **管理后台 `/admin`**：管理招聘来源、数据准入、服务配置和轻量调用审计；质量门和密钥配置不暴露为普通用户概念。

## 当前实现边界

当前代码已经形成五大守护导航、统一职业事件与个人材料底座，以及机会、决策、权益、收支、成长的主要工作区。不同模块的完成度并不相同：

- 机会守护已有市场全景、方向/岗位探索、简历证据分析、目标准备、简历微调和模拟面试主链路；岗位时效与渠道健康属于动态事实。
- 决策守护已有 Offer 档案、事实核对、情景分析、底线、HR 沟通、比较、决定历史和后续入口；部分目标设计仍在继续补齐，不能把页面存在等同于完整业务验收。
- 权益守护已有 P0 合同录入、分段审查、原文定位、条款追问和审查快照；真实扫描件 OCR、多版本比较、页码级定位和报告导出等仍有待验收或实现。
- 收支守护已有候选识别、可信账本、经济事实关系、图表、月结、流式问询和知识入口；更多真实账单/工资条样式、失败恢复和边界准确率仍需持续验收。
- 成长守护的“当下的事—过去的果—未来的路”已进入代码和实际库；项目全局 Agent、进展影响、停滞提示和周/月回顾仍会继续根据真实使用优化。

这些说明代表当前仓库与本机验证边界，不代表远端生产环境已经部署，也不代表用户已完成全部业务验收。最新事实、已知 WIP 和历史证据统一见 [`当前进度与新会话交接`](./zhihu/progress/PROGRESS.md)。

## 数据、隐私与服务边界

- 业务运行、迁移和数据库验收只支持 MySQL；动态迁移头、表结构和运行数据以当前代码、目标数据库只读查询及数据库架构文档为准。
- `zhihu` 保存产品主数据与清洗后的市场事实，`market_raw` 保存招聘采集原文与处理轨迹，`pin_legacy_staging` 只保存历史迁移审计证据。
- 招聘数据只有经过来源校验、标准化、去重和版本化质量门后，才进入机会守护的岗位主库。
- AI 由管理员在服务端统一配置；完整密钥不进入前端、日志或 Git。调用日志只保存必要的功能、状态、耗时和用量信息，不保存 Prompt 或业务原文。
- 个人附件原件存放在私有 `UPLOAD_DIR`，只能经过用户鉴权接口读取；数据库与附件目录必须配对备份。
- 外部模型或 OCR 处理遵循页面披露、场景授权和最小必要范围；未授权内容不应因跨守护复用而扩大出站范围。
- 最新仓库不再包含历史参考项目，运行时不依赖仓库外参考代码、数据库或服务。

数据库唯一结构与合法数据流见 [`职护当前数据库结构`](./zhihu/docs/data/current-database-architecture.md)，AI/OCR 配置与审计边界见 [`职护服务配置说明`](./zhihu/docs/ai-configuration.md)。

## 仓库结构

- `zhihu/zhihu-frontend`：Next.js Web，承载五大守护、今日总览、个人中心、知识和管理后台。
- `zhihu/zhihu-backend`：FastAPI 业务 API，承载用户、材料、职业事件、守护记录、AI 编排和 MySQL 迁移。
- `zhihu/market-data`：招聘来源治理、浏览器采集、Raw、标准化、去重、质量门和岗位晋级。
- `zhihu/docs`：当前产品、架构、数据、开发和验收文档。
- `zhihu/docx`：产品蓝图及历史开发计划；当前状态以进度文档为准。
- `scripts`：工作区检查、MySQL 迁移与本地服务脚本。
- `.github`：持续集成和依赖更新配置。

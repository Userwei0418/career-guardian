# 决策守护当前实现

- 生效日期：2026-08-16
- 状态：当前运行基线
- 主入口：`/decision`
- 产品问题：Offer 值不值得接受；两份或多份 Offer 应该如何按自己的条件选择

## 1. 当前闭环

```text
书面 Offer / 口头意向
  → 建立可持续维护的 Offer 档案
  → 确认事实、附件版本和回复期限
  → 查看单份条件化报告
  → 保存 HR 答复并更新事实账本
  → 准备有依据的确认与谈薪话术
  → 与库存中的另一份 Offer 做快照比较（可选）
  → 用户记录接受 / 拒绝 / 暂缓及理由
  → 接受后由权益、收入和成长守护继续承接
```

决策守护只负责帮助用户看清条件、保留依据和组织行动。系统不会替用户向 HR 回复、替用户签约，也不会把分析分数包装成唯一正确答案。

## 2. 用户能完成的事情

### 2.1 Offer 档案

- 上传并保留私有 Offer 原件版本，或先记录口头意向。
- 确认公司、岗位、城市、薪资结构、试用期、工作地点和工时等字段。
- Offer 由用户从外部招聘流程录入，当前产品不从机会守护的收藏或目标岗位推导 Offer，也不在岗位卡片提供“记录 Offer”入口。
- 记录最晚回复时间和当前状态：评估中、暂缓、接受、拒绝或过期。

### 2.2 单份条件化报告

- 事实账本：明确区分已确认、HR 已答复和仍缺失的信息。
- 收入情景：固定收入、浮动收入、额外薪资月份、试用期影响和生活结余。
- 市场位置：只在有可追溯岗位样本时展示样本量、时间窗和统计口径。
- 条件化建议：说明在什么偏好或假设下值得考虑，不输出“系统替你选”的结论。

### 2.3 两份 Offer 比较

- 比较对象只能来自本人已经保存的 Offer 库。
- 比较时冻结两份 Offer 的事实、用户优先级、生活成本等假设和结果。
- 矩阵覆盖收入、城市结余、确定性、工作条件、成长和市场位置；缺失项保持未知。
- 历史比较不会因为之后修改 Offer 而被重写。

### 2.4 HR 确认与谈薪

- 每个问题带稳定事实键，用户可记录 HR 的最新答复与结论。
- 已答复字段进入 decision 事件的私有证据，并立即更新单份报告和比较结果。
- 谈薪准备从已知 Offer 条件、市场样本、回复期限和缺失事实生成优先级、开场话术、底线话术和注意事项。
- 不虚构竞争 Offer、行业承诺或 HR 未说过的话。

### 2.5 最终决定

- 接受、拒绝和暂缓都必须记录理由，之后修改会新增历史记录而不是覆盖旧记录。
- 暂缓必须设置下次复盘时间，并在原 decision 事件中建立待办。
- 接受后幂等建立三项后续事件：
  - 权益守护：收到合同后核对 Offer 承诺。
  - 收入守护：收到首份工资条后核对 Offer—合同—工资。
  - 成长守护：入职后确认 30 天阶段任务。
- 后续事件只是准备入口；没有材料时不能显示为合同已收到、工资已发放或已经入职。
- 如果用户之后修正决定，原决定历史保留；不再适用的接受后事件归档。

## 3. 数据落点

| 业务对象 | MySQL `zhihu` 表 | 关键语义 |
|---|---|---|
| Offer 档案 | `offers` | 当前事实、附件、回复期限、决定状态；`job_target_id` 仅保留历史数据兼容，不作为当前产品入口 |
| Offer 原件 | `personal_attachment_versions` | 私有二进制版本元数据；文件本体在服务端私有目录 |
| 条件化比较 | `offer_comparisons` | Offer/偏好/假设/结果四类不可变快照 |
| HR 答复 | `evidence` | `decision` 事件中的私有用户材料证据 |
| 待确认与后续行动 | `action_items` | HR 跟进、暂缓复盘、合同/工资/成长待办 |
| 最终决定历史 | `decision_records` | 接受、拒绝、暂缓的选择、理由和时间 |
| 跨域承接 | `career_events` | `rights` / `income` / `growth` 事件，以 `offer:<id>` 标记来源 |

所有数据都按登录用户做所有权校验。AI 调用审计只记录用户、功能点、能力类型、耗时、用量和成功失败，不保存 Offer、Prompt 或回复正文。

## 4. 主要接口

| 接口 | 用途 |
|---|---|
| `GET/POST /api/offers/` | 读取和建立 Offer 档案 |
| `GET/PUT /api/offers/{id}` | 读取和维护本人 Offer |
| `GET /api/reports/offer/{id}` | 单份条件化报告 |
| `GET /api/reports/offer/{id}/hr-questions` | 待确认问题 |
| `GET/POST /api/reports/offer/{id}/hr-confirmations` | HR 答复历史 |
| `GET /api/reports/offer/{id}/negotiation-brief` | 谈薪准备 |
| `GET/POST /api/offer-comparisons/` | 比较历史和新建快照比较 |
| `GET /api/offers/{id}/decisions` | 本 Offer 的决定历史 |
| `POST /api/offers/{id}/decision` | 原子记录接受、拒绝或暂缓并处理跨域流转 |

## 5. 当前验收口径

- 自动化：60 个职护后端测试通过；包含用户隔离、Offer 快照、HR 答复、决定历史、暂缓待办和接受后三域幂等流转。
- 前端：ESLint 0 错误；Next.js 16.3.1 webpack 生产构建通过。
- 浏览器：录入 Offer → 接受 → 列表显示决定理由与时间 → 权益守护显示合同核对待办，真实链路通过。
- 迁移：代码和本地 MySQL 都处于 Alembic 唯一头 `20260816_0017`。

## 6. 后续领域边界

决策守护至此可以作为一个完整领域继续被权益、收入和成长守护消费。后续新增功能应优先完善承接领域，不应重新在决策页复制合同审查、工资条核对或长期成长工具。新的决策维度必须能说明它来自 Offer 事实、用户偏好、市场样本还是显式估算。

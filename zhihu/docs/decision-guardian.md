# 决策守护详细设计文档

- 文档版本：V1.0
- 更新日期：2026-08-20
- 文档状态：目标设计；部分能力已有实现，未实现部分不得描述为已交付
- 主入口：`/decision`
- 核心对象：Offer 决策档案
- 上游：机会守护、外部招聘流程、用户上传或记录的 Offer
- 下游：权益守护、收入守护、成长守护

## 0. 文档结论

决策守护不是“AI 给 Offer 打分并替用户选择”，而是：

> 在用户收到书面 Offer 或口头意向后，把模糊条件转成可追溯事实，把复杂取舍转成可以理解和沟通的问题，帮助用户在知道代价、不确定性和个人底线的情况下作出决定，并把最终承诺交给后续守护继续核验。

决策守护守的是**选择过程的质量**，不保证某个选择未来一定正确。

```text
收到书面 Offer / 口头意向
  → 保留原件或原始记录
  → 用户确认字段、来源、单位和周期
  → 识别矛盾、默认值和关键未知
  → 计算保守 / 当前假设 / 条件兑现三种情景
  → 对照个人底线、当前工作或继续求职基线
  → 生成最影响决定的 HR 确认问题
  → 保存 HR 实际回复并形成新的 Offer 事实版本
  → 单份判断或多 Offer 条件化比较
  → 用户记录接受 / 拒绝 / 暂缓、理由和知晓的未知
  → 固化当时事实、偏好、假设、市场依据和结果快照
  → 接受后把同一份最终承诺交给权益、收入、成长守护
```

系统的核心交付不是一个总分，而是：当前是否具备决策条件、哪些未知会改变选择、不同假设下的结果、用户接受的取舍、现在最值得做的一件事、可回溯的事实和理由，以及后续核验所使用的统一基线。

## 1. 用户需求与典型场景

### 1.1 用户真正需要回答的问题

- 这份 Offer 到底明确承诺了什么？
- 哪些是书面事实，哪些是口头表达、用户转述或系统估算？
- 接受后稳定能拿到多少，最坏但合理的情况是什么？
- 城市、通勤、搬迁和生活成本是否可承受？
- 这份工作是否延续目标岗位方向，还是为了收入接受一次偏航？
- 哪两三个问题不问清楚，可能会改变决定？
- 我是在主动选择，还是被稀缺感、品牌、家人或截止时间推着走？
- 如果以后后悔，我能否看见当时为什么这样选？

### 1.2 场景 A：只有一份 Offer

用户容易把“只有一份”理解为“只能接受”，并因回复期限或害怕追问而快速接受口头条件。

产品需要回答：

- 它是否满足用户的最低可接受条件？
- 保守情景下是否还能承受？
- 接受、继续求职、留在当前工作分别意味着什么？
- 哪一条新信息最可能改变选择？

页面不反复引导“两份比较”，默认提供“接受 / 继续求职 / 当前工作”三个基线，并明确：`只有一份 Offer，也不等于只能接受。`

### 1.3 场景 B：两份 Offer

用户真正面临的是“愿意用什么换什么”，而不是简单比较月薪或品牌。

产品需要回答：

- 两份 Offer 是否已经具备同口径比较条件？
- 如果优先现金流、成长、稳定或生活，分别偏向哪一份？
- 哪些未知项使当前比较无效？
- 哪个 HR 回复会使结论反转？

页面先统一币种、周期、固定/浮动、发薪月数和奖金口径，再使用条件式结论；每份 Offer 使用独立的生活成本和兑现假设。

### 1.4 场景 C：三份及以上 Offer

先按硬性底线、事实完整度和回复期限总览，排除明显不满足底线的 Offer，shortlist 到两份后再深度比较。移动端不展示横向宽表。

### 1.5 场景 D：在职跳槽

新 Offer 要与当前工作比较，纳入放弃的奖金/股票/晋升窗口、试用期风险、空档期、搬迁、通勤和已积累的业务信任。不能只计算新旧月薪差。

### 1.6 场景 E：口头意向

口头条件必须明确标注；在书面条件确认前，主行动是请求书面确认，而不是立即接受、拒绝其他机会或提交离职。

## 2. 产品范围与守护边界

### 2.1 决策守护负责

| 守护层 | 用户问题 | 产品输出 |
|---|---|---|
| 事实守护 | Offer 到底承诺了什么 | 原件、来源、版本、单位、周期、确认状态、冲突和未知 |
| 收入判断 | 稳定能拿到多少 | 固定/浮动、试用期、补贴、奖金、税社保估算和三种情景 |
| 市场判断 | 条件处于什么位置 | 同城市、同岗位族、同币种和周期的历史样本位置及质量说明 |
| 生活判断 | 收入是否支持现实生活 | 城市成本、通勤、搬迁、月结余和储蓄目标 |
| 方向判断 | 是否延续目标方向 | 关联目标岗位的 JD、匹配差距、准备记录和显式未知 |
| 沟通守护 | 还要问什么、如何问 | 问题优先级、原因、话术、留意点、HR 回复和行动 |
| 选择守护 | 愿意接受什么取舍 | 必须满足项、重要项、可接受取舍、红线和条件化建议 |
| 决定守护 | 如何保存选择 | 接受/拒绝/暂缓、理由、未知确认、分析快照和跨域交接 |

### 2.2 决策守护不负责

- 不替用户联系 HR、发送消息、谈判或接受 Offer；
- 不保证公司未来稳定、奖金兑现、团队文化或管理质量；
- 不在没有来源时推测公司平台和成长空间；
- 不把历史岗位样本描述为当前实时行情；
- 不提供精确税社保、公积金或法律结论；
- 不复制权益守护的合同审查、收入守护的工资条核对和成长守护的长期执行；
- 不用总分或单一结论替用户选择。

### 2.3 开始与结束

- **开始**：收到书面 Offer、口头意向、HR 条件清单或谈薪后的新版本。
- **接受**：保存最终 Offer 版本、分析快照、理由和知晓的未知，并建立后续承接关系。
- **拒绝**：保存原因和当时条件，关闭当前评估。
- **暂缓**：保存下次复盘时间、原因和仍需获取的信息。
- **条件变化**：生成新版本并重新打开分析，不覆盖旧条件。

## 3. 核心对象与状态

### 3.1 Offer 决策档案

机会守护围绕“目标岗位”；决策守护围绕“Offer 决策档案”。它包含原始材料、结构化事实、字段来源、HR 回复、用户底线、情景假设、市场快照、比较、决定历史、跨域事件和后续结果。

### 3.2 决策状态机

```text
draft → needs_facts → ready_to_ask → ready_to_assess
      → decision_ready → accepted / declined / on_hold / expired
```

| 状态 | 含义 | 页面主行动 |
|---|---|---|
| `draft` | 刚录入，抽取尚未核对 | 核对识别结果 |
| `needs_facts` | 有阻断字段、单位冲突或关键未知 | 先确认关键事实 |
| `ready_to_ask` | 可初步分析，但还有会改变决定的问题 | 整理并询问 HR |
| `ready_to_assess` | 核心事实可用 | 查看现实取舍 |
| `decision_ready` | 无未知阻断项，或用户已明确知晓 | 记录我的决定 |
| `accepted` | 已接受并固化基线 | 核对合同承诺 |
| `declined` | 已拒绝并保存原因 | 查看决定记录 |
| `on_hold` | 暂缓并有复盘时间 | 完成本次复盘 |
| `expired` | 期限已过但没有实际结果 | 记录实际结果 |

状态只表达材料和流程准备度，不表达“应该接受”。

### 3.3 事实状态

| 状态 | 含义 | UI 标签 |
|---|---|---|
| `unknown` | 没有信息 | 待确认 |
| `extracted` | 系统抽取，用户未确认 | 识别结果 |
| `user_confirmed` | 用户核对过 | 用户确认 |
| `hr_reported` | 用户记录 HR 回复 | HR 回复 |
| `written_confirmed` | 书面材料明确 | 书面确认 |
| `estimated` | 系统或用户假设 | 估算 |
| `conflict` | 单位、周期、金额或来源冲突 | 需要先处理 |
| `superseded` | 被新版本替代 | 历史版本 |

未填写、默认值、抽取值、手工值、用户确认、HR 口头/书面答复和合同最终条款必须严格区分，禁止“非空即已确认”。

## 4. 路由与信息架构

| 页面 | 目标路由 | 说明 |
|---|---|---|
| 决策首页 | `/decision` | Offer、截止时间、一个下一步和历史决定 |
| 单 Offer 工作区 | `/decision/offers/{offerId}` | 事实、分析、问题、取舍和决定统一工作区 |
| Offer 录入 | `/offer/new` | 上传、粘贴、手工、口头意向 |

## 5. 决策首页 `/decision`

### 5.1 页面目标

用户 5 秒内知道：当前有几份 Offer、哪份最临近截止、哪份有阻断事实、现在先做什么、决定是否保存。

### 5.2 Hero

- 最大宽度：`1280–1320px`；高度：`280–340px`；
- 左右比例约 `56/44`，圆角 `32–40px`；
- 背景使用温暖米白到浅绿渐变；
- 右侧可使用 Offer 文件、计算器、城市、天平、对话气泡的编辑插画，不使用机器人、霓虹、AI 光球或真人照片。

左侧：

- `决策守护 · 1 份正在考虑`；
- 标题：`先把会改变选择的条件问清楚。`；
- 关怀：`没有完美答案。你只需要知道自己正在接受什么取舍。`；
- 动态短主按钮：`核对关键事实` / `整理 HR 问题` / `查看现实取舍` / `完成本次复盘`；
- 次按钮：`录入另一份 Offer`。

右侧状态：正在考虑、临近截止、阻断事实、已有决定和最近回复期限。

### 5.3 “现在先做”行动卡

Hero 后只给一个行动：状态、标题、为什么优先、所属 Offer、需要确认几项和主按钮。

```text
需要先处理
确认浮动收入的单位和周期
当前记录为 60,000 元/月，与月薪 7,500 元明显冲突，继续计算会放大误差。
[去核对事实]
```

### 5.4 Offer 卡

排序：已过期未记录结果 → 最早回复期限 → 阻断事实数量 → 最近更新时间。

展示名称、公司/岗位/城市、书面/口头、原件、期限、状态、事实状态、第一优先项、最重要问题，以及 `继续判断` 主按钮和 `记录决定` 次入口。不展示未经校验的总分。

### 5.5 多 Offer 与历史

- 一份 Offer：与当前工作或继续求职比较；
- 两份 Offer：开始条件化比较；
- 三份以上：紧凑总览和 shortlist；
- 已完成决定默认收起，接受和拒绝均使用中性反馈。

### 5.6 空状态

> 有文件可以上传，只有微信、电话或口头条件也可以先记录。信息不全没关系，职护会告诉你还需要确认什么。先记录不等于接受，系统也不会替你联系 HR。

主按钮：`开始录入`。不展示虚构示例数字。

## 6. 单 Offer 工作区

### 6.1 顶部

固定展示返回入口、Offer 名称、公司/岗位/城市、书面/口头、期限、当前状态、最后事实更新时间和分析是否过期。主行动随状态变化。

### 6.2 决策准备度

展示事实不足 / 可沟通 / 可评估 / 可决定、阻断问题、非阻断未知、已确认来源数和当前下一步。

出现以下情况停止收入结论和最终建议：

- 公司主体、岗位、币种或薪资周期未知；
- 月薪、固定、浮动之间数量级冲突；
- 月度和年度金额无法区分；
- 发薪月数来源不明或不合理；
- 不同书面来源冲突；
- 新版本仍使用旧分析；
- 关键金额来自默认值而非确认值。

系统保留原输入，但显示：`这组数字目前不可安全计算，请先确认 60,000 元是年度奖金、年度绩效还是月度浮动收入。`

### 6.3 Offer 事实账本

分为主体与机会、收入结构、工作条件、时间地点、福利保障和其他承诺。

每行展示：字段名、当前值、单位/周期、状态、来源、原文片段、确认时间和历史。

重点字段：

- 主体、公司、岗位、部门、职级、汇报对象、雇佣类型、工作方式；
- 币种、固定月薪、浮动金额及周期、绩效规则、发薪月数、奖金条件、补贴、股权、签字费、调薪；
- 试用期时长和工资、转正标准、工作地点、工时、值班、加班、调休、出差、假期；
- 回复期限、入职日期、办公地点、远程和搬迁。

交互：默认展开阻断项和最近变化；修改时确认来源；影响计算的字段变化后旧分析立即 stale；不静默覆盖历史；正式更新生成新版本。

### 6.4 现实价值与三种情景

收入字段通过一致性检查后才展示：

| 情景 | 口径 | 含义 |
|---|---|---|
| 保守底线 | 只计明确固定部分，未知奖金和浮动按 0 | 最坏但合理的现金流 |
| 当前假设 | 使用用户选择的兑现比例和生活成本 | 当前比较假设 |
| 条件兑现 | 明确列出需要全部兑现的条件 | 上行情景，不等于承诺 |

结果包括固定现金、月/年估算到手、试用期差异、生活支出、月/年结余、公积金、搬迁/通勤成本和与基线的差异。

每个数字可展开“怎么算的”：Offer 事实、规则、用户假设、规则版本、适用日期和未计入项。

用户可调整生活支出、浮动兑现、额外月份兑现；实时预览不自动形成历史，点击 `保存本次假设` 才生成快照。滑杆说明为“情景，不是概率”。

### 6.5 市场位置

只有岗位族、城市、币种、周期明确，样本和新鲜度达标且不是 fixture 时才显示分位。

显示 P25/P50/P75、Offer 区间、样本量、data_mode、统计窗口、计算时间、方法版本、来源和观察时间。

降级文案：

- `样本不足，暂不判断市场位置`；
- `这组数据只适合做历史参考`；
- `Offer 与样本口径不同，暂不比较`。

### 6.6 目标岗位上下文

关联后复用 JD、岗位事实、匹配差距、技能证据、能力路线、模拟面试和准备投入。只回答方向是否一致、职责是否变化、准备是否仍适用和哪些成长信息未知；不能仅凭关联或公司名判断成长价值。

### 6.7 我的底线与取舍

分为必须满足、很重要、可以接受取舍。支持收入、成长、确定性、强度、城市、专业方向、平台、通勤、家庭/健康/照护/搬迁和自定义红线。

- 最多突出 3 个优先项；
- 红线不参与加权平均；
- 无事实支撑的维度保持未知；
- 偏好保存失败不能静默忽略；
- 本次决策使用本次快照，不依赖以后变化的全局档案。

### 6.8 HR 确认与谈薪

问题优先级：阻断计算 → 触发红线 → 改变比较 → 影响后续核对 → 一般补充。首屏最多展示 3 个。

每题包含类别、为什么问、话术、留意点、实际回复、来源、是否明确、确认的具体值、是否需书面核对和下一步。

保存回复后：原文作为私有证据 → 用户确认归一化事实 → 生成新版本 → 旧分析/比较 stale → 重算受影响模块 → 提示“这次回复改变了什么”。不能只因点击“已明确”就将未知变成书面事实。

谈薪只使用真实经历、已知条件、有质量说明的市场样本、明确偏好和回复期限。输出最多两个诉求、依据、开场、替代项和需要书面化的条件；不虚构竞争 Offer，不自动发送。

### 6.9 版本与证据

默认折叠，可查看原始附件/粘贴文本、各版事实、字段变更、HR 回复、分析使用版本、市场和规则版本、确认人和时间。薪酬、合同和决定历史不得静默覆盖。

## 7. 多 Offer 总览与比较

### 7.1 总览

展示期限、书面/口头、公司/岗位/城市、固定收入口径、阻断事实、第一优先项、目标岗位关联和分析 stale；按最早期限排序。

### 7.2 可比门槛

币种不同、月薪与年包混用、固定/浮动未拆、奖金周期不同、发薪月数不明、书面/口头关键条件差异或任一 Offer 有阻断冲突时，先统一口径，不用 `0` 补未知。

### 7.3 两份深度比较

比较稳定固定收入、三种情景、生活结余、市场位置、目标方向、工作强度、信息确定性、期限、红线和机会成本。

- 每份 Offer 独立生活成本、浮动兑现和额外月份兑现；
- 用户选择的维度必须真实进入逻辑；
- 没有实现逻辑的维度不允许选择；
- 保存冻结 Offer、偏好、假设、市场和结果；
- 事实变化显示 stale 和变化摘要，用户主动重新比较。

允许：`如果优先短期现金流，A 当前更有利。`、`A 的工时未知，目前不能判断生活质量。`

禁止：`A 综合评分 87，建议选择 A。`、`B 公司更稳定。`、`你应该接受 B。`

### 7.4 三份以上

紧凑总览、按红线排除、shortlist，最多选两份深比较；保留排除理由。

## 8. 最终决定交互

### 8.1 决定弹层

- 允许用户随时记录真实决定，但有阻断时先展示 preflight；
- 不默认接受、拒绝或暂缓；
- 三个选项视觉权重一致；
- 选定后才显示相应确认按钮。

必填：理由、最重要取舍、是否知晓未知；接受时选择最终 Offer 版本，暂缓时设置复盘时间，拒绝时可选择是否用于以后偏好学习。

Preflight 展示阻断事实、未知、红线、情景假设、期限和 stale 状态。若仍决定，主动勾选：`我知道目前仍有以上未知，仍按当前信息记录决定。`

### 8.2 保存快照

绑定 Offer 版本、事实状态、偏好、预算/生活成本、市场、规则、HR 回复、比较、未知、理由和时间。修改决定新增历史，不覆盖。

### 8.3 反馈

- 接受：中性说明条件和未知已保存，后续由三个守护域核对；
- 拒绝：说明拒绝不会否定此前投入；
- 暂缓：说明暂时不能确定不是失败，并展示复盘时间。

## 9. 跨守护交接

- 权益：`等待合同材料`，继承最终 Offer 承诺；
- 收入：`等待首份工资条`，继承 Offer 和合同薪酬基线；
- 成长：`等待入职或用户启动`，继承目标岗位和前 90 天预期。

交接携带 `offerId + decisionRecordId + eventId + actionId`；后续材料复用对应事件，不依赖浏览器“上一次 Offer”，不重复创建平行事件；Outcome 回流根决策事件。

## 10. UI 视觉设计

### 10.1 视觉气质

关键词：温和但不软弱、专业但不审判、有依据但不过度数据化、清晰表达未知、不制造“AI 替你选”的压迫感。

### 10.2 色彩语义

| 语义 | 建议色 | 使用范围 |
|---|---|---|
| 主品牌/可继续 | 墨绿、青绿 | 主行动、已确认事实、导航 |
| 待确认 | 琥珀黄 | 未知、沟通、截止提醒 |
| 阻断冲突 | 珊瑚红/浅红 | 单位矛盾、stale、红线冲突 |
| 系统估算 | 浅蓝 | 假设、情景、市场参考 |
| 历史/已替代 | 灰 | 旧版本、已关闭 Offer |
| 用户选择 | 紫灰 | 偏好、取舍和决定快照 |

颜色不能是唯一状态表达，必须同时有文字和图标。

### 10.3 卡片与层级

- 一级决策卡圆角 `24–32px`，二级事实卡 `16–20px`；
- 同一屏不超过一个实心主按钮；
- 阻断项置顶，不使用大面积警报红；
- 详细计算、来源和历史进入折叠层；
- 事实与估算视觉分离；
- 金额右对齐，单位紧邻数值；
- 未知显示“待确认”，不得显示 `¥0`、`0 个月`或默认百分比。

### 10.4 图标与插画

可使用 Offer 文件、计算器、对话气泡、城市、通勤、路标、天平、日历和便签。避免法槌/裁决印章、机器人、AI 光球、大量金钱符号，以及庆祝接受或羞辱拒绝的情绪化画面。

## 11. 移动端与响应式

- `<768px` 单列；`768–1199px` 只在短卡片使用双列；`>=1200px` 使用完整工作区；
- 顶部固定显示 Offer 名称、期限和当前下一步；
- 比较按维度逐项展示 A/B，不使用横向宽表；
- 底部固定操作是当前下一步，不能固定为“接受”；
- 决定弹层使用 bottom sheet；
- 事实账本默认只展开阻断项和变化项；
- 事实行在窄屏转为上下结构，不横向滚动。

## 12. 可访问性与安全交互

- 状态标签有可读文本，不只靠颜色；
- 弹层打开后焦点进入标题，关闭后回到原按钮；
- 支持 Escape 关闭非阻断弹层；
- 表单错误与字段关联；
- 金额、日期、百分比包含单位；
- 动态重算使用 `aria-live` 提示完成，不连续朗读滑杆每一步；
- 截止时间同时显示日期和相对时间；
- 复制话术不会自动发送；
- 外部文件打开明确提示私有材料边界。

## 13. 人文关怀设计

人文关怀不是增加鸡汤，而是：不因只有一份 Offer 就推动接受、不因暂缓制造失败感、不把拒绝视为浪费、把下一步缩小到 1–3 个问题、保存已经完成的核对、允许用户带着明确知晓的未知作决定，以及不用分数制造伪确定性。

推荐文案：

- `先记录不等于接受，系统也不会替你联系 HR。`
- `只有一份 Offer，也不等于只能接受；先看它是否满足你的底线。`
- `你不需要一次弄懂所有条件，先确认会改变选择的几件事。`
- `向 HR 问清条件不是不知足，而是在认真对待双方的承诺。`
- `没有完美答案。这里保留的是你在当时事实下愿意接受的取舍。`
- `暂时还不能确定，不代表你做得不好；给自己一个明确的复盘时间即可。`
- `拒绝一份机会不会否定此前的投入。`

禁止文案：

- `AI 建议你接受。`
- `综合评分最高。`
- `错过这份就没有更好的。`
- `公司很稳定。`
- `薪资绝对有竞争力。`

## 14. 真实性与计算门禁

### 14.1 默认值

- 未填写的发薪月数不作为 12 薪事实；
- 未填写的试用期不作为 0 个月；
- 未填写的试用期工资不作为 80%；
- 缺城市不静默使用杭州并呈现为 Offer 事实；
- 通用估算明确标为“通用基线”；
- 未知金额不得格式化为 `¥0`。

### 14.2 跨字段校验

至少覆盖：固定 + 浮动是否显著超过总月薪、浮动是否其实是年度金额、发薪月数、奖金周期、试用期时长和工资比例、城市/地点/主体冲突、币种/周期，以及不同来源对同一字段的冲突。

### 14.3 市场门禁

- 展示 `data_mode`、统计窗口和计算时间；
- 设定最低样本量；
- 同城市、岗位族、币种、周期才比较；
- stale 只能作为历史参考；
- fixture 不进入正式判断；
- 来源和方法不可用时保持未知。

### 14.4 规则时效

税、社保、公积金和城市成本规则至少包含适用地区、版本、生效日期、来源、简化说明和不适用情形。产品统一使用“估算”，不使用“精确到手”“官方结果”。

## 15. 数据模型目标设计

在现有 `Offer / CareerEvent / Evidence / GuardianFinding / ActionItem / DecisionRecord / Outcome` 上增量补齐。

### 15.1 `OfferRevision`

保存 `offer_id`、`revision_no`、结构化事实快照、`created_reason`、`supersedes_revision_id` 和时间。每次用户正式确认或 HR 更新生成新版本。

### 15.2 `FactAssertion`

逐字段保存 `subject`、`field_key`、`value_json`、单位/币种/周期、来源证据、来源类型、验证状态、置信度、观察时间、确认人/时间和被替代关系。

### 15.3 `DecisionAnalysisRun`

每次正式分析保存决策事件、Offer 版本、偏好、计算规则版本、市场快照、假设、输出、未知、引擎版本、生成时间和 stale 原因。最终 `DecisionRecord` 关联一次运行。

### 15.4 `EventLink`

保存父子事件、关系、来源决定、业务对象、幂等键和时间，确保合同、首薪和成长承接同一次接受决定。

### 15.5 市场与规则快照

保存查询口径、岗位族、城市、币种、周期、P25/P50/P75、样本量、data_mode、统计窗口、方法版本、来源、观察时间和税社保规则版本。

## 17. 加载、空态、异常与过期

### 17.1 加载与降级

- Offer、报告、市场、HR 回复分别加载；
- 市场失败不阻断事实页；
- 计算失败保留事实；
- 超时说明哪部分不可用；
- 不使用无限旋转。

### 17.2 空态

- 无 Offer：录入；
- 口头意向：请求书面确认；
- 无市场样本：不展示空图表；
- 无 HR 回复：展示优先问题；
- 无第二份 Offer：使用当前工作/继续求职基线；
- 无偏好：先设置最低条件。

### 17.3 异常

- 数值冲突停止相关计算；
- 来源冲突并列展示；
- 偏好保存失败允许临时预览但不生成“已保存分析”；
- HR 回复失败保留输入并提示重试；
- 决定失败不创建下游事件；
- 交接部分失败返回已成功/失败项，支持幂等重试。

### 17.4 stale 规则

Offer 字段、HR 回复、偏好、市场、税社保规则或生活成本假设变化时，历史分析标记 stale。历史可查看，但显示“当时的结果”。

## 18. 隐私与安全

- Offer、HR 回复、谈薪、预算均为私有材料；
- 所有接口做所有权校验；
- 普通日志不输出原文；
- AI 审计不记录 Offer、Prompt 或回复正文；
- 附件私有下载；
- 用户可删除 Offer、附件、回复和衍生分析；
- 不在 URL 中传完整收入、预算或回复正文；
- 埋点只记结构化状态和 ID。

不优化 Offer 接受率、AI 建议采纳率、平均分和被推动完成决定的速度。

- `decision_comparison_saved`

## 21. 分批实施建议

### 第一批：事实账本与决策安全门

三态及多来源事实、默认/未知分离、字段来源、单位/数量级校验、冲突阻断、Offer 版本、无默认接受的 preflight。这是最高优先级，不应先增加更多评分、图表或视觉包装。

### 第二批：单 Offer 决策工作台

接受/继续求职/当前工作基线、最低条件和红线、三种情景、一个下一步、3 个 HR 问题、回复归一化和正式分析快照。

### 第三批：多 Offer 条件化比较

active 总览、shortlist、每份独立假设、真实偏好维度、条件式结论、stale 和响应式比较。

### 第四批：决定、提醒和跨域连续性

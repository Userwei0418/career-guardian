## 0. 文档结论

权益守护不是 Offer 决策流程的延长，也不以 HR 沟通、谈判或代替用户决定是否签署为主要能力。它是一套面向普通劳动者的合同审查工作台：

> 用户只要有一份劳动合同或相关协议，就能独立上传或粘贴、解析、审查、定位风险原文、理解实际影响并保存审查结果。Offer 仅作为可选对照，不是使用前提。

第一期核心闭环：

```text
上传文件 / 粘贴文字
  → 私有保存原件
  → 立即进入审查进度页
  → 解析正文和劳动合同关键字段
  → 本地条款分段与个人信息脱敏
  → AI 分段解读 + 本地规则复核（模型不可用时只保留规则结果）
  → 风险结论绑定原文
  → 用户查看并保存审查快照
  → 保存合同与审查记录
  → 重新打开 / 归档 / 安全删除
```

字段修正后重审、合同多版本、PDF 页码级定位和报告导出属于 P1，不纳入当前 P0 已完成口径。

系统不以风险数量生成“安全分”，不输出“这份合同可以放心签”“某条款一定违法”等替代专业判断的结论。

## 1. 用户与场景

### 1.1 主要用户

- 第一次签劳动合同的应届生；
- 入职 0～3 年、缺少劳动合同知识的职场新人；
- 收到竞业、保密、培训服务期或补充协议的劳动者；
- 希望回看既有合同、定位关键原文或比较修订版本的用户。

### 1.2 支持材料

第一期支持：

1. 劳动合同；
2. 实习协议；
3. 竞业限制协议；
4. 保密及知识产权协议；
5. 培训服务期协议；
6. 补充协议；
7. 解除或离职协议；
8. 其他个人职场协议。

### 1.3 不应成为前置条件

- 不要求先录入 Offer；
- 不要求先建立目标岗位；
- 不要求填写 HR 回复；
- 不要求用户先懂劳动法；
- 不要求一次把所有字段填完整。

## 2. 产品范围与边界

### 2.1 负责

| 能力 | 用户问题 | 产品输出 |
| --- | --- | --- |
| 材料保留 | 原合同是否还能找回 | 私有原件、文件名、版本、时间、解析状态 |
| 结构化识别 | 关键条件写在哪里 | 劳动合同字段、识别来源、对应原文、未知项 |
| 条款审查 | 哪些内容值得重点看 | 优先关注、建议核对、一般提醒和未发现明显问题 |
| 通俗解释 | 复杂条款是什么意思 | 劳动者视角的影响说明，不使用企业法务术语 |
| 原文定位 | 结论依据在哪里 | 风险卡与原文片段、页码或文本位置联动 |
| 结果留存 | 以后能否回看 | 审查快照、规则版本和生成时间；报告导出为 P1 |
| 版本比较 | 修订后变化了什么 | 字段变化、新增风险、移除风险和原文变化 |
| 可选对照 | Offer 与合同是否一致 | 仅在用户主动关联 Offer 后显示结构化差异 |

### 2.2 不负责

- 不替用户决定是否签署、拒绝或谈判；
- 不自动联系 HR 或发送消息；
- 不把用户引入冗长的 HR 对话记录流程；
- 不宣称替代执业律师或正式法律意见；
- 不把 AI 判断包装成确定法律结论；
- 不把工程合同的工期、工程款、质保金、签证、施工范围等字段和规则迁入劳动合同；
- 不用合同风险总分或 A～F 等级暗示合同安全程度。

## 3. 旧项目复用边界

### 3.1 可以迁移

- 多格式文件上传与文件校验；
- 私有文件存储；
- PDF / DOCX / TXT 文本解析；
- 扫描件 OCR 的任务状态、轮询和失败恢复设计；
- 文件、解析结果、审查结果分层持久化；
- 规则优先、AI 辅助解释、失败后保留规则结果；
- 风险项与命中原文绑定；
- 原文高亮；
- 审查快照；
- 同一合同多文件版本；
- 版本字段和风险变化对比；
- 合同归档；
- 审查报告导出。

### 3.2 必须改写

- 工程合同字段改为劳动合同字段；
- 企业/甲方视角改为默认劳动者视角；
- 工程合同规则改为劳动合同规则；
- 企业后台表格改为当前职护的陪伴式工作台；
- 风险分数改为可解释的关注等级和数量；
- 技术化 provider 状态改为简洁的“规则审查 / AI 辅助 / 降级说明”。

### 3.3 明确不迁移

- 工程款、结算、质保金、工期、签证、工程验收、发票税务规则；
- 企业、个人、工人三视角切换；
- 面向管理员的十项筛选宽表作为普通用户主页面；
- “合同健康分”“A 级合同”等伪精确结论。

## 4. 信息架构

### 4.1 `/rights` 权益守护首页

页面控制在桌面 2～3 屏，默认只展示合同审查相关信息：

1. Hero 与上传入口；
2. 我的合同；
3. 当前需要关注的审查结果；
4. 和当前合同相关的知识。

空状态直接提供：

- `上传合同`；
- `粘贴合同文字`；
- `先看看能审查什么`。

页面必须明确：`没有 Offer 也可以独立审查。`

### 4.2 合同录入

首屏只要求放入材料，不要求用户先手填整套字段。

- 拖拽或选择文件；
- 粘贴文字；
- 选择材料类型；
- 合同显示名称可选；
- 关联已有 Offer 可选，默认不关联；
- 展示格式、大小、隐私和解析能力边界。

### 4.3 合同审查工作台

桌面使用“原文条款块 + 连线 + 审查卡”三段式工作台：

- 左侧：只展示与本次结论相关的原文条款块，保留原始文本和稳定条款编号；
- 中间：从条款块连到对应审查卡的曲线，未选择项弱化；
- 右侧：关注等级、通俗解释、下一步核对项和结论来源；
- 点击审查卡，会同步高亮对应条款和连线；
- 左侧条款卡只显示摘要；“查看原文”用独立模态框打开完整本地原文，不把长文本继续撑在工作台里；
- 右侧每条解读提供“继续追问 / 让模型解释”，在独立模态框内围绕当前条款对话；服务端按当前审查快照读取最近三轮已持久化且已脱敏的问答，只发送该段脱敏条款、当前结论和本次问题，不信任前端伪造历史，也不发送原件或整份合同；
- 移动端不绘制连线，也不重复展示一整列原文；原文查看和条款追问沿用全屏友好的模态框。

长耗时模型调用不得占用“开始审查”的浏览器请求。上传或粘贴成功后立即持久化合同与任务状态并跳转到 `/contract/review?contractId=...`：先显示本地读取状态；条款分段写入后，左侧按顺序出现真实原文片段，右侧明确等待模型；只有完整、通过证据门禁的模型结果持久化后才逐项显示。这里是阶段驱动的渐进呈现，不宣称模型 Token 流式输出。

刷新页面、切换路由或后端进程重启后，页面都以 MySQL 中的 `extracting / processing / reviewing / ready / failed` 和快照 `queued / running / success / partial_success / failed` 为准继续展示，不依赖原浏览器请求存活。某一模型批次失败时保留其他已完成批次和本地规则结果；全部批次失败时只展示规则结果。

顶部只展示：

- 合同名称、材料类型、版本；
- 解析状态和审查时间；
- 优先关注、建议核对、一般提醒数量；
- 当前 P0：`重新审查`；
- P1 目标：`上传新版本`、`导出报告`。

### 4.4 合同记录管理

每份合同提供：

- 查看审查；
- 修改显示名称和材料类型；
- 归档；
- 删除。

当前 P0 已实现查看审查、修改名称/类型、归档和安全删除；查看/下载原件与上传新版本列入 P1。

删除必须二次确认，并明确删除范围；已有跨域历史引用时可以只归档或阻断删除，不能静默截断事实链。

## 5. 劳动合同字段

第一期结构化字段：

- 合同名称和类型；
- 用人单位；
- 劳动者；
- 合同期限；
- 入职日期；
- 岗位、部门和级别；
- 工作地点与调动范围；
- 工时制度；
- 基本工资、固定工资、绩效、奖金和补贴；
- 试用期时长、工资比例和考核方式；
- 社保公积金；
- 年假及其他假期；
- 加班和调休；
- 保密和知识产权；
- 竞业范围、期限、补偿和违约责任；
- 培训服务期；
- 调岗、解除和离职通知；
- 争议解决；
- 其他缺失或模糊条款。

当前 P0 每个识别字段保留：值、`extracted / candidate / blank_in_source / unknown` 状态、质量说明和对应原文。系统先在本地判断材料更像完整劳动合同、专项协议、员工手册/规章制度或其他用工材料；员工手册里的通用工资、试用期、地点等不得当作个人合同已确认事实。置信度、用户修正记录和“修正不覆盖原始识别”的版本链属于 P1 数据能力。

## 6. 风险卡规范

审查项关注级别只有：

- `important`：先看这里；
- `review`：建议核对；
- `note`：条款解读。

没有形成证据充分的审查项时单独显示空态，不伪造 `clear` 结论。

单条风险固定展示：

1. 合同怎么写；
2. 这句话是什么意思；
3. 可能怎样影响劳动者；
4. 建议重点核对什么；
5. 当前规则版本和结论来源。

当前 WIP 同时记录模型供应商、模型、提示词版本、脱敏版本、规则版本、审查方式和发送条款数量。内置确定性规则继续记录 `rule_version` 与 `built_in_rule`；AI 结论记录 `ai_model`，同一条款同时命中时记录 `ai_model_and_rule`。系统不把旧库中缺少司法辖区、依据和生效时间的规则冒充已治理规则。

没有命中原文的“缺失项”必须明确标为：`当前材料中未找到对应约定`，不能伪造引文。

## 7. 规则与 AI

### 7.1 规则负责

- 明确关键词和结构化条件；
- 数值、期限和比例核对；
- 缺失项检查；
- 规则来源、适用地区和更新时间；
- 可复现、可审计的结论。

### 7.2 AI 负责

- 对本地已切分、已脱敏条款做语义分类和补充解读；
- 语义相近条款识别；
- 通俗解释；
- 摘要和阅读顺序；
- 规则未覆盖处的辅助提示。

用户对单条审查结论追问时，AI 只获得该结论对应的一段脱敏条款和必要对话上下文。回答必须明确证据边界；返回原文依据时仍需通过逐字引用校验。追问目前用于即时理解，不作为合同事实修订，也不替用户作签署决定。

可选的 Offer—合同一致性检查采用“模型语义核对 + 本地确定性规则兜底”：模型只读取已确认的 Offer 结构化字段和合同中与月薪、地点、试用期、奖金有关的脱敏条款；每个差异必须标注来源和可回指原句。模型未完成时只展示并明确标注本地规则结果，不把长句截取冒充合同事实。

AI 结果必须带 `ai_model` 来源；与规则同条款同分类命中时合并为 `ai_model_and_rule`，不得静默覆盖规则结论。AI 调用失败时返回规则审查，并向用户说明本次没有 AI 补充，不得伪装成功。

### 7.3 模型发送边界

模型调用前必须在后端本地完成以下步骤：

1. 将合同正文切成带稳定 `clause_id` 和原文位置的条款段；
2. 排除身份、签署等与劳动条件审查无关的段落；
3. 脱敏用人单位、劳动者、法定代表人、地址、出生日期、身份证号、手机号、邮箱和银行卡号；没有显式字段标签但具有明确公司/组织后缀的主体名称也在本地替换；
4. 只选取工资、试用期、工时、岗位地点、社保、休假、竞业、调岗、解除等必要条款，并限制条款数与总字符数；
5. 在发出请求前再次执行直接标识符检查；未通过则阻断调用，只保留本地规则结果。

明确不得发送：PDF/DOCX/图片原件、文件名、完整合同正文、附件路径、用户 ID、联系方式和未脱敏主体名称。`ai_invocation_logs` 只记录功能点、供应商、模型、成功/失败、耗时和可得 Token，不记录 Prompt、合同正文或模型完整响应。

### 7.4 模型结果门禁

- 每一项必须返回现有 `clause_id`；
- `evidence_quote` 必须是该脱敏条款中的连续原句，否则整项丢弃；
- 只允许白名单分类和 `important / review / note` 三种关注级别；
- 模型“重点”最多 3 项，避免把整份合同渲染为高危；
- 未提供带版本的法规依据时，禁止引用法律名称、法定上限或声称“根据法律规定”；
- 模型不得猜测金额、期限、城市、法律效力或公司意图，不替用户决定是否签署；
- 没有任何证据通过门禁时，本次状态记为失败并回退规则审查。

## 8. 数据设计

第一期复用当前 MySQL 和私有附件体系：

- `contracts`：用户合同档案和当前结构化事实；
- `personal_attachment_versions`：用户私有合同原件；
- `career_events / evidence / guardian_findings`：可选的统一证据与守护结论底座；
- `contract_review_snapshots`：保存合同版本、字段、条款分段、审查项、摘要、规则/提示词/脱敏版本、模型供应商与型号、审查方式、AI 状态、发送条款数量、分批完成数、文档位置/类别覆盖和仅含计数的脱敏报告；
- 后续新增合同文档版本表：保存每次上传的解析全文和解析状态。

Offer 外键保持 nullable。无 Offer 的合同必须可以创建、审查、保存、归档和删除；报告导出属于 P1。

`contracts.linked_offer_id` 是非唯一外键：一份合同最多归入一份 Offer，一份 Offer 可以归组多份劳动合同、竞业/保密协议或补充协议。列表和审查页展示“第 N / M 份合同材料”，但每份文件仍拥有独立原件、解析状态和审查快照，不把多个合同覆盖成一个版本。

## 9. 第一阶段开发范围

P0：

1. 新增本设计文档和劳动合同数据契约；
2. 合同文件上传与粘贴入口；
3. 使用私有附件存储保存原件；
4. PDF / DOCX / TXT 本地解析；图片和无文字层 PDF 进入本地中文 OCR，并持久化已读页、OCR 页、空白页和失败原因；
5. 劳动合同字段抽取的确定性第一版；
6. 扩充劳动合同规则并移除风险分；
7. AI 分段解读与本地规则合并，失败时诚实降级；
8. 审查结果与调用元数据持久化；
9. 风险原文直接展示；
10. `/rights` 独立空态、合同列表和上下文知识；
11. 合同归档与安全删除；
12. Offer 可选关联，不影响任何主流程。

P1：

- 真实扫描件 OCR 质量分级、表格/印章版面验证和可选人工校正文；
- 原始 PDF 页码级高亮；
- 合同多版本与版本比较；
- 审查报告 PDF 导出；
- 规则来源治理和地区口径；
- 提供带版本、适用地区和生效时间的法规上下文后，再允许模型引用具体法律口径。

## 10. 当前实现与验证状态

### 10.1 当前工作区已实现

- `/rights` 独立工作台：无合同空态、上传/粘贴入口、合同列表、审查次数、归档和安全删除；
- `/contract/new`：PDF / DOCX / TXT / PNG / JPG 入口，粘贴文本可直接保存并审查；图片和无文字层 PDF 只在本地尝试 OCR，依赖不可用或结果不足时明确停止，不生成虚假结论；
- 私有附件与所有权校验：文件原件保存到本人附件版本，不能读取或操作其他用户合同；
- 确定性劳动合同字段识别与 `labor-contract-v4` 规则审查；未知字段保持未知，不生成安全分；明确写明“不构成/不旨在/不实行竞业限制”的条款不会仅因出现“竞业限制”关键词而触发缺少补偿告警；
- `labor-contract-clauses-v4` 脱敏模型审查：本地按页清理、结构化分段和脱敏，最多三批均衡覆盖前中后及不同类别，只发送必要条款；提示词明确 `[……已脱敏]` 表示原文存在内容，不是未填写，并由解析层再次过滤模型误报；逐项校验 `clause_id + evidence_quote`，与规则合并并支持部分成功/规则降级；
- 身份证脱敏覆盖连续 18 位、旧式 15 位及 PDF/OCR 常见的空格、中点和连字符分隔形式；替换和出站安全阻断共用同一识别模式。原文隐私视图另做展示层遮罩，原件仍保持未改写；
- `labor-contract-follow-up-v3` 单条款追问：原文与模型对话均在独立模态框；模型只收到当前脱敏条款和必要上下文，回答中的原文依据继续执行证据门禁，异常引用会先纠正一次、再按明确边界安全降级，且不能要求用户恢复已脱敏身份信息；成功问答按用户、合同、当前审查快照、条款和核对项持久化；
- `offer-contract-consistency-v2` 一致性核对：模型对已确认 Offer 字段与相关脱敏合同条款做语义比较；脱敏值导致无法比较时只能标 `uncertain`，不能标 `missing`。本地规则补齐模型未覆盖的字段，并在页面展示核对方式、模型状态、来源与合同依据；
- 合同审查快照：保存合同版本、文档哈希、字段、条款段、审查项、摘要、审查方式、模型/提示词/脱敏/规则版本及 AI 状态；相同合同内容与全部版本一致时才复用；
- 桌面“原文块 + 连线 + 审查卡”，移动端“审查卡 + 对应原文”；点击审查卡会切换对应条款和连线高亮；
- Offer 只作可选关联；没有 Offer 也能完成录入、审查、回看、归档和删除；
- 上传/粘贴请求只保存原件与可恢复任务后立即返回；后台 worker 本地解析、分段并调用模型，审查页轮询持久化状态，不再等待 37～45 秒模型请求后才跳转；

## 11. 验收标准

### 11.1 功能

- 无 Offer 用户可以上传或粘贴劳动合同并得到审查结果；
- 原文件、解析文本和审查结果均在 MySQL/私有附件域有可追溯记录；
- 风险项能显示命中原文，缺失项不伪造原文；
- 重新打开页面仍能读取同一审查结果；
- 规则审查失败和 AI 降级不会伪装成完整审查；
- 用户可以归档或在安全边界内删除合同；
- 可选关联 Offer 后才出现附加一致性检查。

### 11.2 真实性

- 未识别字段保持未知；
- 不使用工程合同字段和规则；
- 不展示合同安全分；
- 不输出确定违法、有效或可签署结论；
- 不把测试夹具和演示合同描述为用户事实；
- 正式运行只使用 MySQL。

### 11.3 前端体验

- 桌面首屏能直接上传材料，并在同一屏看到已有合同；
- 1280px 桌面审查页无横向溢出，风险与原文双栏可用；
- 390px 手机审查页单列展示，原文节选无需折叠；
- 键盘可操作，焦点和错误提示明确；
- 页面不通过多个大卡重复引导同一上传入口；
- 知识模块按合同类型和实际风险召回，不使用养老金等无关内容填充。

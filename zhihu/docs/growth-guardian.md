# 成长守护详细设计、交互基线与实现状态

- 文档性质：成长守护唯一、持续维护的产品基线
- 更新日期：2026-08-25
- 文档状态：目标设计与当前实现状态并存；未实现能力不得描述为已交付
- 主入口：`/growth`
- 核心对象：成长计划、阶段目标、行动、成长证据、复盘快照、用户确认的能力事实
- 上游：个人档案、目标岗位、Offer 决策、入职交接、模拟面试和用户主动设定的目标
- 下游：今日待办、职业档案、简历、机会匹配、决策守护、权益守护和收支守护

## 0. 产品结论

成长守护不是课程商城、打卡工具、绩效监控或一个抽象的“能力分数”。它要解决的是：用户从知道差距，到真正完成行动，再把成长变成可复用证据的长期闭环。

```text
成长起点
  → 用户确认基线
  → 制定 30 / 60 / 90 天计划
  → 执行少量当前行动
  → 记录真实证据
  → 周期复盘
  → 用户确认新的成长事实
  → 回流简历、机会、决策、权益与收支守护
```

系统必须始终区分三件事：

- 市场或岗位要求什么；
- 用户已经确认自己具备什么；
- AI 根据现有证据建议用户下一步做什么。

AI 不能因为用户看过课程、完成一次打卡或上传一份材料，就自动认定用户“掌握了能力”“完成了目标”“应该晋升”或“应该跳槽”。成长事实必须由用户确认，并且能够回到支撑它的行动与证据。

## 1. 用户真正需要解决的问题

### 1.1 入职适应

- 接受 Offer 后，前 30、60、90 天最重要的结果分别是什么？
- 哪些人、业务、工具和规则需要优先了解？
- 当前哪些行动最重要，而不是一次性列出几十条任务？
- 试用期目标是否清楚，哪些承诺需要留下证据？
- 到转正节点时，能否快速回顾自己做过什么、取得了什么结果？

### 1.2 能力提升

- 目标岗位反复要求哪些能力，我已经确认具备哪些？
- 哪些差距最影响当前目标，先补哪一个最划算？
- 学习和工作任务如何转化为可验证的项目、作品、反馈或业务结果？
- 一段时间后，能力变化是用户真实成长，还是只是完成了学习活动？

### 1.3 职业调整

- 当前岗位还有没有值得继续积累的空间？
- 什么时候应该继续深耕、尝试内部机会，或重新评估外部机会？
- 过去的成长证据能否直接用于简历、面试和岗位匹配？
- 薪资、职责、工作边界或发展承诺发生变化时，其他守护能否得到明确提醒？

## 2. 产品范围与明确边界

### 2.1 成长守护负责

| 守护层 | 用户获得的结果 |
| --- | --- |
| 起点守护 | 从 Offer、目标岗位或用户自主目标建立可核对的成长基线 |
| 计划守护 | 形成可编辑、可版本化的 30 / 60 / 90 天计划 |
| 行动守护 | 首页只呈现当前最重要的 1—3 项行动及其截止时间 |
| 证据守护 | 把项目、作品、反馈、结果和复盘记录为用户所有的成长证据 |
| 能力守护 | 以证据支撑的方式记录用户确认的能力变化，而不是自动打分 |
| 复盘守护 | 周、月、阶段节点形成可追溯快照，说明进展、阻塞和下一步 |
| 问询守护 | AI 基于已确认事实和证据解释差距、生成方案并辅助复盘 |
| 知识守护 | 展示与入职、试用期、能力建设、项目复盘和职业调整相关的科普 |
| 交接守护 | 用户确认后，把新事实回流到简历、机会、决策、权益和收支守护 |
| 数据自主 | 查询、编辑、导出和删除自己的计划、行动、证据与复盘记录 |

### 2.2 成长守护不负责

- 不用一个总分评价用户的职业价值；
- 不把课程完成、阅读次数或打卡天数等同于掌握能力；
- 不替管理者监控员工，不采集键盘、屏幕、会议或工作时长；
- 不根据少量市场岗位推断用户必须学习某项能力；
- 不在用户未确认时把 AI 草稿写成正式成长事实；
- 不自动修改简历、个人技能、求职目标或其他守护的正式记录；
- 不把薪资变化、合同承诺或劳动权益判断复制进本模块；
- 不自动建议离职、晋升或转岗；可以给出条件化选项和证据缺口；
- 不把所有成长功能堆在一个超长页面中。

### 2.3 不可破坏的原则

- 程序负责日期、状态、版本、聚合和审计；AI 负责解释与草拟；用户负责确认事实；
- 市场要求、AI 建议和用户能力必须分层保存、分层展示；
- 计划可以修改，但历史版本不能被覆盖；
- 行动完成不自动等于目标完成，目标完成不自动等于能力掌握；
- 所有跨守护写入都必须展示“将写到哪里、写入什么、依据是什么”，并由用户确认；
- 默认只展示当前周期和少量行动，低频能力进入独立页面或抽屉；
- 所有删除、撤销和版本切换都可追溯。

## 3. 三种成长起点

### 3.1 接受 Offer 后开始

决策守护确认接受 Offer 后，可以幂等建立成长事件和一条待办，但这只表示“准备建立入职计划”，不代表用户已经入职。

系统带入的只能是已确认事实：公司、岗位、职责、约定入职日、试用期、Offer 中的成长或绩效承诺。用户确认后形成第一版 30 / 60 / 90 天计划。

### 3.2 围绕目标岗位开始

用户从机会守护选择一个目标岗位或岗位族。程序先从质量合格的岗位样本提取常见技能，再与用户已确认技能对照。样本不足或过期时必须显示 `样本不足` 或 `历史数据`，不能输出伪精确结论。

### 3.3 自主设定当前岗位目标

用户不需要先有 Offer 或目标岗位，也可以直接输入：

- 希望解决的问题；
- 希望在什么时间前看到什么结果；
- 当前已有的基础；
- 可投入时间；
- 哪些信息不希望发送给 AI。

系统可以帮助把模糊目标拆为可核对的阶段结果，但最终目标由用户确认。

## 4. 统一处理链路

```text
选择成长起点
  ↓
程序读取已确认事实与有效证据
  ↓
生成基线草稿和证据缺口
  ↓
AI 草拟 30 / 60 / 90 天结构、行动与复盘问题
  ↓
用户编辑并确认计划版本
  ↓
今日只显示 1—3 项当前行动
  ↓
完成行动并添加结果或证据
  ↓
程序生成阶段汇总，AI 辅助解释
  ↓
用户确认复盘与能力变化
  ↓
按需确认回流到其他守护
```

计划生成、行动完成、能力确认和跨域回流是四个独立确认点，不能合并成一次“全部同意”。

## 5. 前端信息架构与用户体验

### 5.1 `/growth` 主页面

主页面只回答四个问题：现在处于哪个周期、当前最重要的行动是什么、已有怎样的证据、下一次复盘是什么时候。

从上到下建议为：

1. **当前成长周期**
   - 目标名称、来源、计划版本、周期起止日；
   - 30 / 60 / 90 天阶段进度；
   - 下次复盘时间；
   - 一个主按钮：`继续今天的成长任务`；
   - 次按钮：`记录一条成长证据`。
2. **当前重点**
   - 只显示 1—3 项当前行动；
   - 每项展示目的、完成条件、截止时间和所关联目标；
   - 支持完成、延期、拆分、暂缓和添加证据。
3. **阶段时间线**
   - 30 / 60 / 90 天不是三个任务清单，而是三个阶段结果；
   - 点击阶段在侧边抽屉查看目标、里程碑和历史版本，不让页面无限变长。
4. **能力与证据**
   - 展示“已有证据”“待补证据”“用户已确认能力”；
   - 市场技能只作为对照信号，不能与用户能力混在一起。
5. **成长趋势**
   - 展示阶段目标完成度、证据积累和阻塞变化；
   - 不使用没有解释依据的雷达总分。
6. **问一问成长教练**
   - 支持流式输出、安全 Markdown 和回答依据；
   - 只使用用户允许且已确认的事实、计划与证据。
7. **KNOWLEDGE**
   - 三张与当前阶段相关的用户科普卡片；
   - 入口 `查看全部知识 →`；
   - 卡片不展示内部推荐依据、模型规则或系统机制说明。

没有活动计划时，主页面不展示一堆空图表，而展示三个平级起点：`从已接受 Offer 开始`、`从目标岗位开始`、`自己设定目标`。

### 5.2 次级页面和抽屉

| 入口 | 推荐载体 | 原因 |
| --- | --- | --- |
| 完整计划与历史版本 | `/growth/plans/{id}` | 结构复杂、需要稳定 URL 和深度编辑 |
| 成长证据库 | `/growth/evidence` | 需要筛选、搜索、导出与批量管理 |
| 周期复盘历史 | `/growth/reviews` | 低频但需要时间线和版本对照 |
| 单个行动编辑 | 右侧抽屉 | 保持主页面上下文，不跳走 |
| 单个证据详情 | 模态框或抽屉 | 快速查看来源、关联目标和回流状态 |
| 图表明细 | 模态框 | 点击图表不自动滚动到页面底部 |
| AI 对话 | 主页面折叠区；移动端全屏抽屉 | 高频但不能挤压核心行动 |

### 5.3 响应式行为

- 桌面端：当前周期与行动为主列，复盘与证据为辅列；
- 手机端：当前行动置顶，图表和证据按需展开；
- 所有抽屉在手机端改为全屏模态页；
- 计划编辑过程支持自动保存草稿，但只有点击确认才生成正式版本；
- 页面刷新或断网后保留草稿并提示状态，不得把草稿冒充已确认计划。

## 6. 计划、行动、证据与复盘状态

### 6.1 计划状态

```text
draft → active → completed
            ├→ paused
            └→ superseded
```

- `draft`：程序或 AI 生成、用户尚未确认；
- `active`：用户确认的当前计划；
- `paused`：用户主动暂停，保留计划和证据；
- `completed`：用户完成阶段复盘后确认结束；
- `superseded`：被新版本替代，历史仍可查看。

每次正式修改都创建新版本。恢复旧版本也应形成一个新的当前版本，而不是覆盖历史。

### 6.2 行动状态

`pending`、`in_progress`、`blocked`、`completed`、`skipped`、`cancelled`。

完成行动时至少允许用户填写：结果摘要、关联证据、是否达到完成条件。仅点击“完成”可以结束行动，但不能自动改变能力状态。

### 6.3 证据类型

- 项目或作品；
- 可量化业务结果；
- 同事、客户或导师反馈；
- 课程、证书或考试结果；
- 演讲、文章、代码、设计稿等公开或私有产出；
- 会议、复盘或问题解决记录；
- 用户手工确认的其他证据。

证据保留最小必要内容：标题、发生时间、用户摘要、来源引用、隐私级别、关联目标和能力。原文件是否保留由用户单独决定；只保存链接或摘要时要明确提示后续可能无法打开原件。

### 6.4 复盘快照

复盘快照至少记录：

- 本周期原计划与当前版本；
- 已完成、延期、跳过和受阻行动；
- 新增证据；
- 目标完成条件是否达到；
- 用户确认的能力变化；
- 仍缺少的证据；
- 下一周期决定与理由。

AI 可以根据这些事实生成复盘草稿，但用户提交前不进入正式历史。

## 7. 数据模型基线

成长守护复用 `CareerEvent`、`Evidence`、`GuardianFinding`、`ActionItem`、`DecisionRecord` 和 `Outcome` 作为跨域事件图；以下对象用于表达成长域特有结构：

| 建议对象 | 关键字段 | 作用 |
| --- | --- | --- |
| `growth_plans` | `user_id`、`career_event_id`、`source_type`、`source_ref`、`status`、起止日、当前版本 | 计划根与所有权边界 |
| `growth_plan_revisions` | `plan_id`、版本号、完整计划快照、修改理由、确认人和时间 | 可撤销、可追溯版本 |
| `growth_goals` | 阶段、目标、完成条件、优先级、状态 | 30 / 60 / 90 天结果 |
| `growth_milestones` | `goal_id`、截止日、完成条件、状态 | 可核对里程碑 |
| `growth_skill_assessments` | 技能、来源类型、市场信号、用户确认状态、证据充分度 | 分离要求、建议与能力事实 |
| `growth_evidence_items` | 类型、标题、发生时间、摘要、隐私级别、来源引用 | 用户所有的成长证据 |
| `growth_goal_evidence_links` | 目标、证据、关联理由、用户确认 | 多对多证据映射 |
| `growth_check_ins` | 时间、进展、阻塞、下一步、草稿/确认状态 | 轻量过程记录 |
| `growth_review_snapshots` | 周期、聚合指标、复盘正文、确认时间、计划版本 | 稳定的阶段快照 |

所有表必须包含用户所有权或能够经计划/事件严格回溯用户；越权访问统一返回 404。跨表唯一约束、版本号和幂等键必须在数据库层落地，不能只依赖前端。

## 8. 能力判断与证据规则

### 8.1 三层来源

| 层级 | 示例 | 可否直接成为用户能力 |
| --- | --- | --- |
| 市场信号 | 质量合格岗位反复出现某技能 | 否 |
| AI 建议 | 根据目标与证据建议优先提升某技能 | 否 |
| 用户确认事实 | 用户确认，并关联一项或多项真实证据 | 是 |

### 8.2 程序负责

- 计划、目标和行动状态机；
- 日期、逾期、周期与复盘提醒；
- 版本、撤销、所有权和幂等；
- 证据数量、完成率和变化趋势；
- 质量合格岗位样本的确定性聚合；
- 跨守护回流的审计记录。

### 8.3 AI 负责

- 把模糊目标改写为可核对草稿；
- 基于已确认输入生成阶段计划候选；
- 提议目标、行动、完成条件和复盘问题；
- 解释技能差距和证据缺口；
- 将用户事实整理成复盘、简历要点或面试故事草稿；
- 给出多种条件化路径，而不是单一职业决策。

### 8.4 用户必须确认

- 成长基线和正式计划；
- 行动完成、跳过、延期和取消；
- 证据是否真实、归属和隐私级别；
- 目标是否达到、能力是否变化；
- 是否把内容写入个人技能、简历或其他守护。

## 9. 跨守护数据闭环

| 来源/去向 | 允许流转的内容 | 禁止自动推断 |
| --- | --- | --- |
| 决策 → 成长 | 已接受 Offer、岗位、确认职责、入职日期、试用期承诺 | 已实际入职、承诺已兑现 |
| 机会 → 成长 | 目标岗位、质量合格岗位样本、常见技能 | 用户一定缺少某能力 |
| 成长 → 机会 | 用户确认的新技能和证据摘要 | 自动提高岗位匹配分 |
| 成长 → 简历 | 用户选择的项目、结果和证据草稿 | 自动改写并覆盖正式简历 |
| 成长 → 决策 | 阶段复盘、可迁移能力、已确认职业偏好变化 | 自动建议接受或拒绝 Offer |
| 成长 → 权益 | 用户记录的职责、试用期目标或承诺变化 | 自动认定公司违约 |
| 成长 → 收支 | 用户确认的证书、课程等成长投入或收入变化线索 | 未确认费用、工资或报销事实 |
| 成长 → 今日 | 当前最重要行动与复盘提醒 | 一次展示整个计划 |

跨域写入采用“建议卡片 → 查看差异 → 用户确认 → 写入并可撤销”的统一模式。

## 10. AI 问询体验与安全边界

- 默认问题围绕当前计划、阻塞、证据和复盘，不把未确认草稿放入上下文；
- 流式输出必须支持取消、恢复状态、安全 Markdown 和失败重试；
- 每次回答展示使用的数据范围、计划版本和可核对证据；
- 对事实不足的问题回答“尚未核清”，列出需要用户补充的材料；
- AI 不直接调用写接口；所有写入先返回结构化候选；
- 外发前进行最小化和脱敏，私人附件默认不发送；
- 管理页记录功能点、服务、模型、耗时、用量和结果，不保存请求或回答正文；
- 同一用户的相同请求必须有幂等键，断流不得导致重复调用和重复记录。

## 11. KNOWLEDGE

成长守护知识卡应解释用户真正遇到的问题，而不是解释系统如何运行。首批建议覆盖：

- 入职前 30 天先确认什么；
- 如何把试用期目标写成可验收结果；
- 30 / 60 / 90 天计划为什么要以结果而不是课程为中心；
- 怎样给项目结果留下一份可信证据；
- 同事反馈如何转化为可行动建议；
- 什么时候该补基础能力，什么时候该做真实项目；
- 如何判断一项技能已经达到“能独立使用”；
- 项目复盘的五个核心问题；
- 如何把成长证据写成简历成果；
- 职业停滞时先核对哪些信号；
- 内部转岗前应准备什么；
- 学习投入如何与时间和预算协调。

知识卡显示标题、阶段、摘要和标签；详情页给出完整科普、适用条件和更新时间。卡片不展示“推荐依据”“AI 判断规则”或内部版本说明。

## 12. 图表与指标

成长图表服务于复盘，不做装饰性评分：

- 阶段目标完成趋势：折线或阶梯图；
- 当前行动状态：紧凑堆叠条形图；
- 证据类型构成：环形图；
- 目标—证据覆盖：矩阵或进度条；
- 阻塞原因变化：时间线；
- 用户确认能力变化：按月阶梯图，并显示证据数量。

所有图表只统计已确认记录。点击图表在模态框查看明细，保持当前位置，不自动滚动到页面下方。空样本显示原因和下一步，不绘制误导性比例。

## 13. 导出、删除与隐私

个人中心允许导出：

- 当前计划与所有历史版本；
- 行动和状态变更记录；
- 证据目录、摘要和用户选择的附件；
- 周期复盘；
- 用户确认的能力变化和跨守护写入记录。

删除计划时先展示影响范围。用户可以只删除计划、只删除某项证据或删除整个成长事件。被其他守护引用的证据不能静默消失，应先解除引用或保留最小不可反推正文的审计占位。附件删除与结构化证据删除分开确认。

## 15. 开发顺序

### 阶段 A：事实和计划底座

1. 增加成长计划、版本、目标、里程碑、证据、复盘的数据结构和迁移；
2. 完成所有权、状态机、幂等、撤销和审计接口；
3. 将现有技能差距草稿接入计划草稿，而不是直接制造能力事实；
4. 完成单元、MySQL 集成和迁移往返测试。

### 阶段 B：主页面最小闭环

1. 三种起点；
2. 当前周期与 1—3 项重点行动；
3. 30 / 60 / 90 时间线；
4. 记录证据；
5. 阶段复盘并确认第一条能力变化；
6. `/today` 同步当前行动。

### 阶段 C：分析、问询与知识

1. 成长趋势和证据构成图表；
2. 基于已确认事实的流式 AI 问询；
3. 用户视角成长科普；
4. 图表和知识明细使用模态框/独立页面，不拉长首页。

### 阶段 D：跨守护和数据自主

1. 能力与证据回流个人档案和简历草稿；
2. 与机会、决策、权益和收支的建议卡片；
3. 个人中心导出与删除；
4. 桌面、手机、断网恢复、权限和真实登录态验收。

## 16. 验收标准

1. 用户可以从 Offer、目标岗位或自主目标建立计划草稿；
2. 未确认草稿不进入正式成长事实；
3. 每个计划有明确起止日、版本和来源；
4. 用户可以确认、修改、暂停、结束和恢复计划；
5. 每次正式修改都保留历史版本；
6. 30 / 60 / 90 天阶段均有结果和完成条件；
7. 首页默认只显示当前最重要的 1—3 项行动；
8. 用户可以完成、延期、拆分、跳过或取消行动；
9. 行动完成不会自动标记目标或能力完成；
10. 用户可以记录多种类型的成长证据；
11. 证据可以关联多个目标，且关联需要用户确认；
12. 市场信号、AI 建议和用户能力在数据与视觉上分层；
13. 样本不足或过期时不输出伪精确技能差距；
14. 周期复盘能够回溯计划版本、行动和证据；
15. 能力变化必须由用户确认并能够查看依据；
16. 图表只统计已确认记录，点击明细不改变页面滚动位置；
17. AI 支持流式输出、安全 Markdown、取消、幂等和证据引用；
18. AI 不能直接写计划、完成任务、确认能力或回流其他守护；
19. 知识内容是用户科普，不是系统机制说明；
20. 跨守护写入前展示目标、内容、依据和影响；
21. 所有跨守护写入可撤销并有审计；
22. 用户可以导出自己的计划、证据、复盘和能力变化；
23. 越权访问统一返回 404，删除不会破坏其他用户或其他守护数据；
24. 桌面和手机在空状态、有计划、断网恢复、AI 失败和删除场景下完成真实登录态验收。

## 17. 发布口径

只有完成“计划建立 → 当前行动 → 证据记录 → 阶段复盘 → 用户确认能力变化”的真实闭环，才可以称为成长守护基础版可用。

完成图表、AI、知识、导出或某一个跨守护交接，都不能单独替代上述闭环。代码测试通过不等于用户验收，静态页面和演示数据也不得写成正式业务能力。

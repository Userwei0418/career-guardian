# 职护岗位数据质量门

## 目标

质量门回答的不是“这条数据能不能保存”，而是“这条岗位事实是否足以被职护拿给用户做机会、决策和成长判断”。原始数据必须先保存到隔离 Raw 或历史 Staging 以保留证据，但只有质量门判定 `accepted` 的候选事实才能进入 `zhihu.market_*` 产品事实表；用户接口只读这些表。

```text
授权来源 → Raw / 历史 Staging → 来源适配与候选字段映射
                              → 统一质量门
                                 ├─ accepted → 去重 → zhihu.market_*
                                 ├─ duplicate → 不新建岗位，保留统计/来源
                                 └─ quarantined → 隔离，等待补全或人工复核
```

初始规则参数位于 `market-data/policies/job_core_v1.json`，发布后的策略版本保存在 `zhihu.market_quality_gate_policies`，执行器位于 `market_data/quality_gate.py`。Pin 历史迁移和以后 Raw→产品事实晋级会在执行时读取当前生效版本并调用同一个执行器，脚本和来源适配器不得自行决定是否写产品表。

## 业务规则

### 1. 不可妥协的事实

以下任一项不成立，直接进入隔离，不以总分补偿：

- 企业名称和岗位标题存在，能够形成最小岗位身份；
- 来源 URL 是有效 HTTP(S) 地址，持续在线采集必须是 HTTPS；
- 内容哈希是 64 位 SHA-256，可从 Core 回到原始记录；
- 来源观察时间存在，且不能明显晚于质量门执行时间；
- 实时采集岗位必须有达到当前策略最小正文长度的职责、要求或 JD 正文；只抓到标题和地点的空壳记录必须隔离；
- 进入 Core 的写入必须经过质量门，不能由采集器或脚本直接构造 `Job`。

### 2. 标准化后再评分

- 企业：清理空白和别名键，保留来源企业 ID；企业丰富字段缺失不伪造。
- 岗位：规范标题、岗位族、招聘类型、城市、技能标签；技能按规范键去重。
- 薪资：从原始文本识别 K/千、万和月/年/日/小时；年薪折算为月薪用于比较；单位不可靠或上下界异常时清空薪资，不污染分位数，但不因此丢弃整条岗位。
- 时效：历史快照的 `open` 统一降为 `unknown`；持续采集只有在最近 14 天观察到且无过期证据时才可标记 `open`。
- 身份与重复：用企业规范键、规范标题、城市和来源 URL 生成稳定身份键；重复候选不新建 Core 岗位。

### 3. 质量评分

| 维度 | 分值 | 对业务的意义 |
|---|---:|---|
| 企业 + 岗位身份 | 30 | 用户知道“谁在招什么” |
| 可访问来源 | 15 | 能核查岗位事实 |
| 内容哈希 | 5 | 能回溯原始证据 |
| JD 至少 50 字 | 15 | 支撑职责、技能和匹配判断 |
| 标准城市 | 10 | 支撑城市市场和生活成本比较 |
| 发布时间 | 5 | 判断时间有效性 |
| 来源观察时间 | 5 | 判断数据新鲜度 |
| 结构化技能 | 5 | 支撑匹配差距和成长守护 |
| 可信薪资 | 10 | 支撑市场位置和 Offer 决策 |

达到 55 分且不存在不可妥协项才可进入 Core。55 分不是“优质岗位”标签，而是“最小可用事实”门槛；A/B/C 质量等级继续展示给下游，图表还要执行样本量门槛。

薪资、技能和城市缺失采用“字段降级”而不是整条岗位作废，因为一条有真实来源的岗位仍可用于机会发现；但缺失字段不得参与相应统计，也不得由模型猜测补齐。

## 与五个守护领域的关系

- 机会守护：只展示有身份、来源、时效状态和质量等级的岗位。
- 决策守护：薪资分位只使用可信且周期统一的薪资样本，同时返回样本数、时间窗和来源。
- 权益/收入守护：不把市场推断写成用户合同或工资事实，私有材料不进入市场库。
- 成长守护：技能差距只使用岗位明示技能和用户已确认技能，不从 JD 猜测能力深度。

## 新来源接入方式

1. 管理员审批来源条款、用途、允许域名和采集频率。
2. 适配器只写不可变 Raw，并将状态设为 `pending_gate`。
3. 未配置 `promotion_mapping` 的来源即使已审批、已启用也不能启动采集。
4. 采集成功后，来源映射器自动把本次新 Raw 映射为统一 `CorePromotionInput`，不做放行决定。
5. `promote_raw_candidate` 校验 Raw lineage，调用统一质量门。
6. 通过后写产品事实表，并将 Raw 状态更新为 `promoted`；未通过则更新为 `quarantined` 和原因码。
7. 用户 API 永远不查询 `pending_gate` 或 `quarantined` 数据。

公司渠道适配器采用可复用的详情获取顺序：先读取列表项内已加载但可能隐藏的结构化详情；缺失时再点击展开并重读当前项；仍然缺失时写入诊断标记并交由统一质量门隔离。平台规则只负责找到标题、职责和要求，是否准入始终由同一质量门决定，因此同平台企业可直接复用，新增平台也不需要另写入库判断。

## 策略变更

- 管理后台“数据准入”页可以查看当前生效版本、认证岗位数、硬条件、分数阈值、时效参数、薪资上限和九项评分权重。企业、岗位、来源、内容指纹和采集时间是不可关闭的系统证据底线；管理员只能在此基础上追加城市、完整描述、发布时间、结构化技能或可信薪资等更严格硬条件。
- 已发布版本不可原地修改；管理员保存时由服务端生成下一版草稿，修改草稿会清除旧预检结果。
- 草稿必须先对最近最多 500 条 Core 岗位做影响预检，显示预计通过率、隔离数和主要原因，未预检不能发布。
- 发布后新抓取和新迁移数据立即使用新版本。存量 Core 保留原认证版本并继续可查，避免发布瞬间让岗位列表清空；需要收紧存量时，应另行发起可审计的批量重新认证任务。
- 每条 Core 岗位记录 `gate_policy_version`、`gate_evaluated_at`、质量分和原因码，能够解释“为什么这条数据被放行”。
- 管理员浏览器只调用职护后端，市场内部管理令牌不会发送到前端。启动脚本优先使用显式 `MARKET_INTERNAL_TOKEN`，本地缺失时使用 `JWT_SECRET` 做域隔离派生，保证两个服务拿到同一令牌。

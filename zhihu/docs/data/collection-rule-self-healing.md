# 采集解析规则自愈设计

## 目标与边界

招聘站点改版后，选择器、字段路径或分页方式可能失效。职护允许 AI 生成修复候选，但不允许模型直接覆盖正在运行的解析器，也不允许失败任务绕过质量门写入产品主库。

优先修复对象是声明式规则，包括列表容器、岗位卡片、标题、地点、发布时间、详情链接、详情正文和分页规则。只有无法用声明式规则表达的特殊站点，才允许生成兼容代码；兼容代码必须在无密钥、无任意文件写入、默认无外网的隔离进程中运行。

## 自愈流程

1. **识别可修复故障**：页面可访问但规则未命中、解析结果为零、关键字段覆盖率骤降或解析器异常时，标记为 `repair_candidate`。网络不可达、登录失效、条款未审批等问题不交给 AI 改规则。
2. **保留脱敏证据**：保存失败页面的脱敏 DOM、页面地址、平台类型、旧规则版本和错误分类。Cookie、Token、表单值、个人信息及响应头中的认证信息不得进入快照或模型请求。
3. **生成候选规则**：AI 只返回符合固定 JSON Schema 的字段选择器、字段路径、分页策略和解释，不直接修改生效配置。
4. **离线回放**：新规则必须同时回放当前失败快照和该渠道最近若干个成功快照。验证岗位数量、标题覆盖率、公司/渠道身份、链接域名、关键字段覆盖率、重复率和质量门预检结果。
5. **灰度发布**：高置信候选先以 canary 规则运行一次真实采集，Raw 与当前规则隔离对比；达到阈值后才能自动晋级为 active。数量异常放大、关键字段下降或质量门隔离率上升时自动回滚。
6. **人工兜底**：低置信候选、首次出现的平台、需要登录或生成代码的修复必须由管理员查看规则差异和回放指标后发布。

## 版本与审计

后续实现使用三类持久化记录：

- `collection_page_snapshots`：脱敏页面快照及内容哈希；设置保留期限，不保存认证信息。
- `collection_rule_versions`：规则版本、来源、状态、父版本、生成模型、发布人和回滚关系。
- `collection_repair_attempts`：触发任务、故障分类、候选版本、回放指标、canary 结果和最终处置。

规则状态固定为 `draft → replay_passed → canary → active`，失败进入 `rejected`，已撤销版本进入 `rolled_back`。每个渠道始终只有一个 active 版本，采集任务必须记录实际使用的规则版本，保证结果可追溯。

## 默认验收阈值

- 解析岗位数大于 0，且不超过历史基线的合理上界。
- 标题非空率不低于 98%。
- 详情链接全部属于渠道允许域名。
- 公司、渠道和招聘类型身份不能由模型猜测或改写。
- 关键字段覆盖率不得显著低于最近成功版本。
- 回放结果必须能进入 Raw；是否进入 `zhihu.market_jobs` 仍由独立质量门决定。
- canary 失败后保持旧 active 规则，且管理员能够查看失败原因并一键回滚。

## 管理后台呈现

管理员在“数据采集”中看到的是：故障类型、旧规则版本、脱敏快照、AI 修复候选、规则差异、回放前后指标、canary 状态和发布/回滚记录。普通用户页面不展示采集规则或质量门概念。

当前版本已完成职护自有渠道目录、平台规则回退和真实采集链路；本文件定义下一阶段自愈服务的实现约束，不代表 AI 自动发布已经上线。

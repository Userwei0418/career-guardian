## 目标一：完成近期修改审计并合并到 main

### 目标结果

仓库中的近期功能、迁移、文档和运行资产形成一个完整、可重建、无敏感信息、可验证的提交；功能分支推送后安全合并并推送到远程 `main`。

### 必须完成

- 审计工作区全部已跟踪和未跟踪变更，区分运行文件、测试、文档、本地证据和敏感文件；
- 纳入所有被运行代码直接依赖的模块、页面、迁移和正式图片资产；
- 忽略本地生成的截图、构建产物、缓存和环境密钥；
- 统一现行数据库口径为 MySQL + Alembic，不将历史 SQLite 验收记录误写成现行运行方案；
- 明确正式 MySQL 当前版本、代码迁移头和待部署迁移，不把不同环境写成同一个“当前”；
- 更新 README、文档索引、进度、数据库架构、收支守护、腾讯 OCR 和服务配置文档；
- 处理审计发现的接口兼容、流式幂等、管理员日志归因和迁移可逆性风险；
- 检查提交内容不包含 `.env`、腾讯密钥、数据库密码或其他个人凭据；
- 运行与风险相称的后端 MySQL 测试、迁移测试、前端 lint/type/build；
- 提交并推送功能分支；
- 将功能分支快进合并到本地 `main`，推送远程 `main`；
- 最后核对远程分支 SHA、工作树状态和代码迁移头。

### 完成定义

- 新 checkout 能得到完整迁移链和所有运行依赖；
- 正式数据库凭据不再出现在当前文件中；
- 发现于历史提交的凭据已明确要求轮换，未经额外授权不重写 Git 历史；
- 文档不会把 `0030`、`0053`、`0056` 等历史快照混称为现行版本；
- 目标分支和远程 `main` 指向同一已验证提交；
- 没有把测试通过误写为生产部署或用户最终验收。

## 目标二：把成长守护设计为最后一个完整守护模块

### 产品目标

建立“基线—计划—行动—证据—复盘—回流”的长期成长闭环。用户能够从已接受 Offer、目标岗位或自主目标开始，确认一份 30 / 60 / 90 天成长计划，持续执行少量重点行动，记录真实证据，完成阶段复盘，并把用户确认的成长事实按需回流到个人档案、简历和其他守护。

### 第一开发里程碑

完成一条可真实验收的最小闭环：

```text
选择成长起点
  → 生成并确认成长基线
  → 编辑并确认 30 / 60 / 90 天计划
  → 首页显示 1—3 项当前行动
  → 完成行动并记录一条证据
  → 完成一次阶段复盘
  → 用户确认一项能力变化
```

### 必须遵守

- AI 只草拟和解释，不能确认能力、完成任务或决定晋升/跳槽；
- 市场要求、AI 建议和用户能力分层保存；
- 计划、行动、证据、复盘和跨守护写入都可版本化、撤销和审计；
- 首页保持任务导向，低频功能进入独立页面、抽屉或模态框；
- 图表只统计已确认事实；
- 证据坚持最小必要、用户可控和所有权隔离；
- 所有跨守护写入都经过用户确认。

### 交付物

- 产品与交互基线：[成长守护详细设计、交互基线与实现状态](../growth-guardian.md)
- 数据模型与 Alembic 迁移；
- 后端所有权、状态机、版本、幂等和审计接口；
- `/growth` 主页面、计划详情、证据库和复盘入口；
- `/today` 当前行动联动；
- MySQL 集成、迁移往返、前端交互和真实登录态验收证据；
- 完成后同步更新本文、PROGRESS、数据库架构和模块文档。

### 当前实现边界

现有 `/growth` 只有技能差距草稿、市场技能与用户确认技能对照、通用事件/证据/发现/行动写入，以及接受 Offer 后的成长待办。它是可复用起点，不是完整成长守护。

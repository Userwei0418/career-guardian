## 0. 文档结论

收支守护不是两个彼此割裂的页面，也不是“工资守护里附带一个支出功能”，而是一个统一工作台中的两条平等入口：

```text
入口一：收入守护 ─┐
                  ├→ 候选识别与核对 → 统一可信账本
入口二：支出守护 ─┘              ↓
          大图表 → 已确认列表 → 待处理轻提醒 → AI → KNOWLEDGE → 导出
```

两类入口都遵守同一个处理原则：

```text
程序先判断
  → 疑难项自动调用 AI
  → AI 仍无法确定时由用户处理
  → 用户确认后才进入正式账本
```

系统不能静默把 OCR、文件解析或 AI 结果写入正式账本。程序和 AI 只能生成候选、关系建议、解释和待办；正式写入、重复保留、事实合并、拆分、撤销和关键修正都必须由用户确认。

目标状态下，收支守护长期保存的核心不是用户上传过的原文件，而是用户确认后的财务事实及其关系。整张工资条、整张账单截图、原始 CSV/TSV/XLSX/PDF 不作为个人附件长期保存；允许保存识别过程中生成的切图片段、完整 OCR 原文、规范化行数据和结构化候选，用于续办、定位、去重和解释。

由于切图片段可能重新拼接出大部分原图，用户侧文案必须准确表述为：

> 不保存整张原文件；会保存识别切片、OCR 文字和用户确认后的结构化结果。

不得宣传为“图片完全不留存”。

## 1. 用户真正需要解决的问题

### 1.1 收入侧

- 我的工资由哪些项目组成，为什么本月变多或变少？
- Offer、劳动合同、工资条和实际到账是否一致？
- 社保、公积金、个税和其他扣款是否能够解释？
- 是否存在少发、多扣、迟发或漏发？
- 没有关联 Offer、合同时，这份工资条本身说明了什么？
- 奖金、补贴、兼职、副业、经营和其他收入分别有多少？
- 工资条上的实发金额是否真的已经到账？

### 1.2 支出侧

- 微信、支付宝、银行卡长截图能否完整识别，而不是只识别前几十行？
- 哪些记录可以批量确认，哪些存在疑问，为什么有疑问？
- 重叠截图、重复导入和历史已入账记录会不会造成重复计算？
- 钱主要花在哪里，和上月相比变化在哪里？
- 退款、报销、转账、信用卡还款和贷款本金是否被错误算成收入或消费？
- 识别到一半能否退出，下次从候选核对处继续？

### 1.3 统一账本侧

- 同一笔钱出现在工资条、银行卡和微信中时，是否只计算一次？
- 一笔记录拆成多次到账，或多笔记录合并到账时，能否正确关联？
- 所有图表和 AI 回答是否只基于已确认事实？
- 每个数字能否回到对应记录、来源文字、匹配理由和用户确认动作？
- 用户能否撤销错误确认、解除错误匹配并重新处理？

## 2. 产品范围与明确边界

### 2.1 收支守护负责

| 守护层 | 用户获得的结果 |
| --- | --- |
| 录入守护 | 手工、文件、OCR 和自然语言都先形成候选，不直接入账 |
| 工资守护 | 工资构成、扣款、Offer—合同—工资条一致性和实际到账核对 |
| 消费守护 | 长截图完整识别、分类、重复识别、趋势和商户分析 |
| 事实守护 | 多来源记录归并为经济事实，避免重复计算 |
| 关系守护 | 工资到账、内部转账、退款、报销、拆分和合并关系 |
| 分析守护 | 基于已确认账本进行确定性统计、图表、趋势和异常发现 |
| 问询守护 | AI 基于程序计算结果解释收入、支出和守护问题 |
| 知识守护 | 展示与当前问题相关的薪资、税社保、消费和财务知识 |
| 数据自主 | 在个人中心查询、导出、删除自己的结构化收支数据 |

### 2.2 收支守护不负责

- 不替用户认定公司违法，也不把缺少证据描述为少发、迟发或漏发；
- 不把工资条实发金额自动冒充银行实际到账；
- 不把未确认候选计入正式列表、图表、结余或分析问询；
- 不要求用户先维护“我的账户”清单，也不反复询问账户归属；
- 不在证据不足时承诺自动精准识别本人转账，只生成带理由的关系候选；
- 不让 AI 自行计算总额、修改正式账本、自动合并事实或替用户作决定；
- 不保存整张原始工资条、账单截图或原始导入文件作为长期附件；
- 不把 OneBill 的 Java/Vue/H2/JWT、用户体系、厂商 Key 或独立 AI/OCR 配置移植进职护；
- 不因某项能力暂未实现就从完整产品范围中删除。

### 2.3 不可破坏的统一原则

- 收入和支出在入口、账本、图表、问询和报告中平级；
- 缺失字段必须保留为“未知”，不能自动填成 `0`；
- 金额、日期、统计、查重和账本影响由确定性程序负责；
- AI 负责语义理解、疑难关系建议和解释，不直接写账；
- 所有候选在用户确认前都不属于正式财务事实；
- 已确认数据和待核对数据必须在数据层、接口层和视觉层彻底分离；
- 所有确认、合并、拆分和关系操作都必须可撤销、可追溯。

## 3. 核心对象与状态

### 3.1 核心对象

| 对象 | 含义 | 是否参与正式统计 |
| --- | --- | --- |
| 识别来源 | 用户本次输入的工资条、账单、文字或表格 | 否 |
| 识别产物 | 切图片段、完整 OCR 原文、规范化行数据 | 否 |
| 候选记录 | 程序或 AI 提取的待核对工资项目、交易或关系 | 否 |
| 来源观察 | 某个来源中看到的一条记录或证据 | 否 |
| 经济事实 | 用户确认后，现实中实际发生的一次收入、支出、转账、退款、报销或工资权益事件 | 视类型决定 |
| 正式流水 | 经济事实对现金账本产生的已确认记账结果 | 是 |
| 事实关系 | 到账、拆分、合并、内部转账、退款、报销、替代版本等关系 | 决定统计口径 |
| 守护发现 | 少发、多扣、重复、冲突、异常变化等可解释问题 | 否 |

来源观察应保持不可变：它记录“原来源当时看到了什么”。用户修正不能覆盖 OCR 原文或原始解析结果，而应形成新的候选修正或经济事实版本。资金流向和经济性质也必须分开，例如退款是资金流入，但经济性质不是收入。

### 3.2 识别批次状态

```text
processing
  → mapping_required
  → reviewing
  → partially_confirmed
  → completed / cancelled / failed
```

- `processing`：正在切图、OCR、解析或调用识别 AI；
- `mapping_required`：表格字段无法确定，需要用户映射；
- `reviewing`：候选已经生成，等待核对；
- `partially_confirmed`：部分已入账，仍有候选未处理；
- `completed`：全部候选已经确认或排除；
- `cancelled`：用户明确选择“删除本批次”，任务不可续办，切片、OCR 原文、规范化行和未入账候选一并删除；
- `failed`：识别失败，展示可操作的失败原因。

关闭模态框或离开页面只是“暂时关闭”，不等于取消批次，状态保持 `reviewing` 或 `partially_confirmed`。退出页面后可继续的是已经生成的候选、识别切片和 OCR 文字。整张原文件删除后，如果尚未生成任何可续办产物且任务失败，用户需要重新选择原文件。

### 3.3 候选三档状态与核对

| 层级 | 视觉语义 | 判断基础 | 用户操作 |
| --- | --- | --- | --- |
| 高置信 | 绿色 | 关键字段完整、确定性规则闭合、没有冲突和重复风险 | 默认可勾选，支持一键批量记录 |
| 中置信 | 黄色 | 主要字段可用，但存在分类、关系、日期、对象或重复疑问 | 用户修正或明确接受后记录 |
| 低置信 | 红色 | 金额、方向、日期等关键字段缺失或相互冲突 | 必须人工补全或排除，不能直接记录 |
| 精确重复 | 独立阻断标记 | 命中可信外部流水号、来源行或同一内容指纹 | 默认复用并打开已有记录；用户仍可说明原因选择“仍要记录”，且还需再次最终确认 |
| 疑似重复 | 独立醒目标记 | 命中当前批次、重叠截图或正式账本中的相似记录 | 查看对应记录后选择取消录入或仍要录入 |

颜色只是状态辅助，必须同时提供文本、图标和“为什么”说明，不能只靠颜色传达风险。

AI 给出高概率不等于高置信。绿色必须有可复核的确定性证据；仅依赖模型判断的候选至少保持黄色并由用户确认。

AI 可以解释程序产生的置信等级和疑点，但不能靠模型自报概率直接设置或提升绿色等级。

三档颜色表示“当前候选是否具备入账条件”，但内部必须分别保留三类判断：

- **字段识别置信**：金额、方向、日期、商户和来源位置是否完整、相互一致；
- **关系匹配置信**：它与工资到账、转账另一端、退款原支出或报销支出的关系是否有足够证据；
- **重复状态**：不是重复、精确重复或疑似重复。

候选最终颜色取会影响记账口径的最严格结果。一条消费的金额和日期可以是字段高置信，但如果它是否属于内部转账仍无法确定，整条候选不能显示绿色。

### 3.4 事实确认状态

| 状态 | 含义 |
| --- | --- |
| `candidate` | 仍在核对模态框中，不进入正式账本 |
| `confirmed` | 用户已确认，可进入列表、图表和分析 |
| `reversed` | 原确认已撤销，不再参与当前统计，但保留最小审计 |
| `superseded` | 被新版本或新关系替代，历史仍可追溯 |

## 4. 路由与统一信息架构

收支守护只使用五大守护体系中的顶层导航，不在页面内部再放一套“总览 / 收入守护 / 支出守护 / 可信账本 / 问一问”导航栏。

| 页面/弹层 | 目标入口 | 说明 |
| --- | --- | --- |
| 收支守护统一工作台 | `/income` | 两个平等入口、大图表、已确认列表、待处理轻提醒、AI、KNOWLEDGE 和导出入口 |
| 收入录入与核对 | `/income` 内模态工作流 | 工资条、其他收入、材料关联、到账确认 |
| 支出录入与核对 | `/income` 内模态工作流 | 手工、文件、长截图、候选分级和重复处理 |
| 既有工资条页 | `/payslip` | 迁移期兼容，目标能力应从统一收入入口到达 |
| 既有薪资工具 | `/salary` | 作为计算和解释工具，不单独形成第二套账本 |
| 个人数据导出 | 个人中心 | 导出已确认结构化数据和分析结果 |

统一工作台顺序：

```text
五大守护顶层导航
  ↓
收支守护标题、月份和关键状态
  ↓
[ 收入守护：识别工资条 / 记录其他收入 ]   [ 支出守护：识别长截图 / 记录一笔 ]
  ↓
大尺寸收支分析与核心图表
  ↓
已确认收支列表与多维筛选
  ↓
待处理批次的轻量提醒入口（点击打开核对模态框）
  ↓
AI 收支问询与建议
  ↓
KNOWLEDGE：和当前问题相关的知识
  ↓
个人中心导出与数据管理
```

待确认候选不在主页面伪装成正式流水，也不进入图表。主页面只显示轻量提醒，例如“还有 2 个批次、17 条候选待核对”，点击后回到原核对模态框继续处理。

## 5. 入口一：收入守护

### 5.1 支持的录入方式

工资条应支持：

- 页面逐项输入；
- CSV、TSV、XLSX 文件导入；
- 工资条图片 OCR；
- 手机截图和 PDF；
- 已录入工资条的查看、编辑、删除和重新识别；
- 同一月份重复工资条识别、差异比较和版本提醒；
- 除工资外的奖金、补贴、兼职、副业、经营、投资和其他收入手工录入或导入。

以上都属于完整范围。当前是否已实现只在本文“当前实现状态”章节标记，不因为实施顺序而移出计划。

### 5.2 工资条识别字段

一份工资条识别后，至少提取：

- 工资所属月份；
- 发薪单位；
- 应发工资；
- 基本工资；
- 绩效、奖金、加班费；
- 各类津贴和补贴；
- 社保个人缴纳；
- 公积金个人缴纳；
- 个税；
- 考勤、餐费及其他扣款；
- 实发工资；
- 工资条日期；
- 约定发薪日；
- 实际到账日期；
- 工资条中的其他企业自定义项目。

自定义项目不能被丢进一个不可解释的总数。每一项至少保留名称、金额、收入/扣除方向、来源文字、识别状态和用户修正记录。

不能把工资条中没有的字段自动填成 `0`；缺失必须保留为“未知”。“未知”“明确为 0”“不适用”是三个不同状态。

### 5.3 识别后询问是否关联材料

识别完成后，系统询问用户是否关联：

- Offer；
- 劳动合同；
- 两者都关联；
- 暂不关联。

允许关联一个或多个材料，因为可能出现：

- Offer 写一套工资；
- 合同写另一套工资；
- HR 口头或书面回复又是另一套口径；
- 同一合同存在补充协议或多个版本。

系统不能自行决定哪份材料正确，而是分别展示来源、版本、差异和冲突，由用户选择当前采用的解释或继续保持待确认。

若 Offer 或合同已经存在于职护其他守护中，收支守护复用其结构化事实和引用关系，不重复保存材料原件。

### 5.4 关联 Offer/合同时：完整收入守护

```text
Offer 承诺
   ↓
合同约定
   ↓
工资条应发与扣除
   ↓
实际银行/钱包到账
```

提供的守护包括：

- Offer—合同—工资条一致性；
- 约定工资和工资条应发是否一致；
- 试用期工资是否符合约定；
- 奖金、绩效、补贴是否兑现；
- 应发减去各项扣款是否等于实发；
- 为什么本月工资变少或变多；
- 社保、公积金缴费基数和比例是否合理；
- 个税、专项附加扣除解释；
- 是否存在无法解释的扣款；
- 少发、多扣、迟发、漏发；
- 与上月工资条的项目变化对比；
- 发现问题后生成需要询问 HR 的问题和材料清单；
- 展示与当前问题相关的薪资、社保、公积金和劳动权益知识。

其中“迟发、漏发”必须同时具备约定发薪日和实际到账证据才能判断；没有证据只能提示“尚未核清”，不能直接认定公司违法、少发或漏发。

### 5.5 暂不关联材料时：工资条自身分析

用户不关联 Offer 或合同时，仍然提供：

- 工资构成和扣除构成；
- 应发、扣除、实发的算术核对；
- 基本工资、绩效、奖金、补贴占比；
- 社保、公积金、个税和其他扣款的通俗解释；
- 与历史工资条的项目和金额变化；
- 异常新增、消失或波动项目提醒；
- AI 对工资条各部分的问询和解读；
- 与工资条字段相关的 KNOWLEDGE。

未关联材料时，系统不能作出“违反 Offer/合同”的结论，因为不存在可用的承诺基线。

### 5.6 工资所属月份与实际到账时间

工资必须同时保留两个时间维度：

- **工资归属月份**：例如“7 月工资”，用于工资构成、跨月对比和权益判断；
- **实际到账时间**：例如“8 月 10 日到账”，用于现金流和迟发判断。

工资条实发金额是权益证据，不自动等于现金到账：

```text
Offer/合同 → 应发 → 扣款 → 工资条实发
                           ↓ 匹配/结算
                      实际到账流水
```

- 已找到对应银行或钱包到账时，系统生成匹配候选，用户确认后只计算一次收入；
- 没有到账证据时，系统生成“待确认工资到账”候选，询问用户是否已经收到、实际金额和到账日期；
- 用户确认收到后，才创建或关联正式收入流水；
- 用户尚未确认时，工资条只进入工资分析，不进入正式现金账本；
- 工资条实发和实际到账不一致时，现金账本以实际到账为准，差额进入收入守护问题；
- 同一月份多份工资条不能简单相加，必须先判断补发、重发、更正或多个雇主。

工资条确认和现金到账确认必须是两个独立状态：

```text
SalaryStatement：extracted → confirmed → superseded
SettlementStatus：unmatched → partially_settled → settled
LedgerEntry：candidate → confirmed → reversed / superseded
```

- 工资构成分析 AI 可以读取用户已经确认的 `SalaryStatement`；
- 现金流图表和现金流问询只能读取已经确认的 `LedgerEntry`；
- 部分到账时分别展示已到账合计和待到账余额；
- 来源只有日期时只保存日期，不能补造 `00:00` 或其他时分秒；来源包含可信时间时才保存准确到账时间。

### 5.7 收入侧 AI 与知识

AI 可以回答：

- “为什么这个月工资少了 826 元？”
- “这笔扣款在 Offer 和合同里有依据吗？”
- “社保、公积金和个税分别是什么？”
- “实发和到账差 300 元，可能需要确认什么？”
- “帮我整理一段问 HR 的话。”

金额差异和字段对照由程序计算，AI 只解释已经计算出的结果并引用对应工资项目、材料条款、到账记录和知识来源。

## 6. 入口二：支出守护

### 6.1 支持的录入方式

支出应支持：

- 页面手工录入一笔小账；
- 自然语言录入一笔或多笔收支；
- CSV、TSV、XLSX 导入；
- 微信、支付宝、银行账单导入；
- 单张票据或普通截图 OCR；
- 微信、支付宝等长截图 OCR；
- 多张连续截图批量识别；
- 已生成候选的继续处理、编辑、排除和删除；
- 已确认支出的编辑、撤销、拆分和重新分类。

### 6.2 长截图强支持

长截图不能只通过放宽一个像素上限来实现，完整链路应包括：

```text
校验真实图片
  → 自动缩放和方向纠正
  → 按内容切分为有重叠的片段
  → 保存识别切片
  → 分片 OCR 并保存完整 OCR 原文
  → 识别跨片段交易行
  → 去除重复标题和重叠记录
  → 程序生成候选
  → 疑难项自动调用现有 AI
  → 进入三档核对模态框
```

用户体验要求：

- 常见长截图不再直接提示“图片像素尺寸过大，请缩小后重试”；
- 系统自动完成安全缩放和切片，并展示“正在识别第 3/8 段”；
- 单个片段失败时允许只重试该片段；
- 交易行跨越切片边界时能够重新拼接；
- 重叠区域中的同一笔交易只生成一个候选；
- 多张连续截图中重复出现的上一页尾部记录能够识别；
- 不能因 OCR 文本长度或单次模型候选数量限制而静默丢掉后半部分交易；
- 识别进度和逐片诊断默认可展开查看，完成后允许折叠，避免大段技术状态挤占候选核对空间；
- OCR 引擎必须返回文字、文本框坐标和置信度，后续程序才能可靠地把“分类标题、时间、商户小字和金额”配成同一交易行，并在原切片中框出证据；
- 每个切片都必须提供“查看详情”，展示实际送入 OCR 的派生图片、原图纵向范围、供应商/模型、文字行数、平均置信度、候选覆盖和按坐标重组后的 OCR 原文，并支持上一片/下一片；
- 腾讯返回的文字不能只按 `y/x` 顺序直接交给通用文本解析器。微信账单的金额与分类位于同一横行、商户位于下一行，程序必须先按坐标聚类成同一交易事实；日期标题中的日收支汇总要合并为上下文并排除，防止商户拿到下一笔金额；
- 目标主识别引擎采用腾讯云 `GeneralAccurateOCR`，不再计划引入 PaddleOCR；本机继续负责图片校验、缩放、重叠切片、候选生成、去重和账本门禁；
- 长截图候选复用 OneBill 已验证的腾讯 OCR 坐标配行、重叠切片、日期上下文和去重思路，但不移植它的用户体系、密钥或其他厂商配置；
- 一张长截图会按切片分别调用云 OCR，免费额度按 API 请求而不是按原图消耗；失败重试也可能增加调用量，已完成切片和同内容批次必须复用已有结果；
- 启用后派生图片切片会发送给腾讯云，不能继续使用“图片原件不会发送给模型”或“原图不出站”作为笼统文案；前端必须在首次使用前明确披露处理方、发送内容、用途和留存边界；
- 现有 AI 只读取程序筛出的最小脱敏文字或必要局部结果，负责补充商户语义和解释歧义，不能改写已由程序确定的金额、日期、方向，也不能自行入账；
- 腾讯云未配置、免费额度耗尽、超时或认证失败时，链路必须降级到当前本机 Tesseract 和人工核对，不能静默丢交易或自动开通付费。

当前 `main` 代码基线已实现腾讯云高精度 OCR 适配：普通图片和长截图切片均可优先调用 `GeneralAccurateOCR`，保留文字行坐标用于候选框选，记录不含图片正文的调用次数与状态，并支持软上限和 Tesseract 降级。真实 `794×18578` 截图的 14 片识别已完成，用户确认商家名称明显改善；验收同时发现旧解析器把“商户下一行”错误配到“下一笔金额”，现已改为按腾讯坐标聚类分类、商户和金额，并增加逐片详情及候选来源框选。错误批次 #18 已由用户删除，没有入账。一次额外整图 A/B 只识别到 5 个日期标题、10 个抽样商家命中 4 个、平均置信度约 84.9%，规则层仅形成 24 个稳定候选且留下 96 个低置信锚点，因此当前不以整图单次调用替代切片。

`cashflow-long-image-v13` 已把固定高度切片升级为自适应完整行切片：程序在目标高度附近寻找安全空白间隙，避免切片尾部只保留半条交易；相邻切片仍保留必要重叠，并对日期、金额、方向、时间和交易文本一致的重叠记录确定性合并。`cashflow-ocr-rules-v5` 同时建立可扩展的“来源标签 + 商户/说明语义”分层分类：账单中明确且与系统分类等价的标签可以直接归类；“服务 + 美团平台商户”等非等价语义只能形成同类批量确认建议，不得擅自变绿；规则仍无法稳定判断时才交现有 AI，AI 仍不确定则由用户逐笔处理。

清洁账本上的真实腾讯 OCR 批次 #24 已完成正式 admin 登录态验收：14/14 个自适应切片成功、生成 99 条候选、0 条缺日期、0 条疑似重复、0 条已存在和 0 条格式错误。页面实际执行了一次共同年份/币种确认、一次 3 笔“保留未知交易对方”确认，以及“餐饮 19 条、其他支出 5 条、交通 2 条”三个分类组的批量确认，最终为 97 绿、2 条待人工、0 已入账。剩余两条均是第 13/14 片中 OCR 交易行关联不完整，候选详情可展示切片定位和对应框选；系统没有猜测或静默入账。批次 #23 暴露的 4 条同片同额误查重已通过通用 OCR 行门禁修复，并由 #24 的 0 疑似重复结果复验。此前批次 #22 已完成桌面和 `390×844` 手机布局、切片详情及候选来源框选检查；#24 本轮完成桌面实际批量操作，未重复宣称新的手机验收。实际开通、最小权限密钥、关闭后付费、环境变量、图片出站和验收步骤见 [`腾讯云 OCR 配置与费用安全边界`](./tencent-cloud-ocr-configuration.md)。

整张原图无论识别成功、失败、超时还是用户取消，都不能作为长期附件遗留；已经生成的切片、OCR 文字和候选按识别批次继续管理。

### 6.3 支出候选字段

一条支出候选至少包含：

- 发生日期和可用时的准确时间；
- 金额和币种；
- 收入、支出或转账方向；
- 商户或交易对方；
- 消费分类；
- 固定、日常弹性、一次性、可报销或其他支出性质；
- 支付平台或来源；
- 订单号、流水号或可用的外部标识；
- 交易状态；
- 备注或商品摘要；
- 来源切片、OCR 文字定位和识别理由；
- 重复或关系匹配建议；
- 程序判断、AI 判断和仍需人工确认的问题。

缺少金额、方向或日期等关键字段时保持未知并进入红色；不能通过默认值让候选看起来完整。

### 6.4 三档核对模态框

识别完成后，以统一模态工作区展示候选列表：

```text
识别完成：共 126 条
  绿色 103 条，可批量记录
  黄色  15 条，需要确认
  红色   5 条，需要补全
  疑似重复 3 条，需要选择
```

交互要求：

- 绿色记录默认可勾选，但仍需用户点击“一键记录所选”；
- 黄色记录直接展示疑点、AI 建议和可修改字段；
- 红色记录突出阻断字段，修正前不能入账；
- 精确重复默认复用并打开已有记录，不创建第二份相同来源观察；用户明确选择“仍要记录”时必须说明原因，系统保留覆盖证据并要求最终入账确认；
- 疑似重复记录展示所有达到提示门槛的现有记录及各自理由；存在多个等价候选时明确说明“无法自动确定”，不能只让模型挑一条；
- 用户可以选择“暂不处理”“排除这条录入”“不是同一笔，作为新事实入账”，以及在存在可用的跨来源正式记录时选择“归入已有经济事实，作为辅助证据”；
- 选择“归入已有经济事实”时，必须展示目标正式记录、匹配理由、分配金额和统计影响；来源观察仍保留，但被分配为辅助证据的金额不重复进入收入、支出、图表和 AI 统计；
- 同一来源的重复导入不能伪装成新的辅助证据，只能复用、排除，或由用户说明为什么确实是另一笔交易；
- 批量确认只处理当前勾选且满足条件的候选；
- 部分确认成功后，其余候选继续留在批次中；
- 任何 AI 建议都不能绕过用户确认按钮。

### 6.5 暂存退出与继续处理

用户可以在候选已经生成后随时关闭模态框。系统保存：

- 识别切片；
- 完整 OCR 原文；
- 规范化表格行；
- 候选字段；
- 程序和 AI 判断理由；
- 用户已经修改的字段；
- 已确认、待处理和排除状态。

下次进入 `/income` 时，通过轻量提醒返回同一批次继续处理。没有确认的候选仍不出现在正式列表、图表或分析问询中。

### 6.6 截图重叠、精确重复、疑似重复和跨来源合并

重复处理至少覆盖四层，且不能混为一个状态：

1. **切片重叠去重**：单张长截图或多张连续截图的重叠区域出现同一行，由程序在生成候选前合并；
2. **精确重复**：可信外部流水号、来源行身份或稳定内容指纹完全一致，默认复用并展示已有记录，不创建第二份来源观察；只有用户说明原因并完成最终确认时才能作为例外另行记录；
3. **疑似重复**：金额、方向、时间、商户或摘要高度相似，但仍可能是两笔真实交易，必须由用户选择；
4. **跨来源事实合并**：工资条和银行到账、银行转出和微信转入等不是删除一条“重复记录”，而是保留多份来源观察并关联到同一经济事实。

匹配时综合使用平台流水号、订单号、金额、方向、时间、商户、摘要和规范化指纹。命中精确重复时默认打开并复用已有记录，但不剥夺用户“仍要记录”的显式决策权；命中疑似重复时必须：

- 告诉用户为什么认为重复；
- 展示对应的已确认记录；
- 默认不重复入账；
- 允许用户明确选择“作为新事实入账”或“归入某条已有经济事实”；
- 在最终确认时重新校验目标记录、方向、币种、可分配金额和用户当时看到的匹配集合；校验结果变化时退回核对，不能静默改换目标；
- 记录这次人工判断，避免相同批次再次反复询问。

在删除整张原文件前可以计算不可逆内容摘要，用于识别完全相同的重复上传；摘要只用于幂等和查重，不能替代交易级、切片级和经济事实级去重。

### 6.7 特殊支出口径

- 退款应关联原支出并冲减消费，不计为普通收入；
- 报销应关联一笔或多笔可报销支出，单独展示已报销、待报销和差额；
- 信用卡还款不重复计算原消费，利息和手续费单独作为支出；
- 贷款发放和本金偿还属于融资现金流，不计为劳动或经营收入，也不冒充消费；
- 微信、支付宝与银行卡之间的内部资金移动不计收入或支出；
- 无法确定口径时保持候选状态，不猜测写账。

## 7. 统一经济事实与精准匹配

### 7.1 为什么不能只有交易列表

同一笔钱可能同时出现在工资条、银行卡和微信中。系统需要把它们理解为同一个经济事实的多个观察或相互关联的事实，而不是机械地计算三次：

- 工资条：应发、扣款和净发的权益证据；
- 银行到账：真实现金流；
- 微信或支付宝转账：可能只是资金换了存放位置；
- 退款：原支出的冲销；
- 报销：与可报销支出相抵；
- 信用卡还款、贷款本金：账户或负债变化。

### 7.2 事实关系

关系必须拆成两类语义，不能只实现一张含义模糊的关联表：

1. **来源观察 ↔ 经济事实**：多对多，表达一条观察拆成多个事实、多条观察共同证明一个事实；保存证据角色、分配金额、匹配状态、理由和确认信息；
2. **经济事实 ↔ 经济事实**：表达结算、转账配对、退款、报销、拆分、合并和替代；保存关系类型、分配金额、当前状态和版本。

统一模型至少支持：

- `evidences`：某条来源观察为经济事实提供证据；
- `settles`：实际到账结算工资条或其他应收；
- `transfers`：两端记录属于一次内部资金移动；
- `refunds`：退款冲销原支出；
- `reimburses`：报销对应一笔或多笔垫付支出；
- `splits`：一条来源记录拆成多个经济事实；
- `merges`：多条来源记录共同组成一个经济事实；
- `supersedes`：新工资条或更正记录替代旧版本。

关系必须保存关联金额。这样才能表达部分退款、部分报销、分次发薪和多笔合并到账，而不是只有“有关联/没关联”。同时满足：

- 一条来源观察的已分配金额不能超过其可分配金额；
- 退款累计不能超过原支出剩余可退款金额；
- 报销累计不能超过待报销余额；
- 工资已到账合计和待到账余额由程序校验；
- 关系状态区分 `candidate`、`confirmed`、`reversed` 和 `superseded`；
- 已撤销或已替代的关系不参与当前统计；
- 每次确认、修改和撤销保存确认人、确认时间、规则版本和账本修订号。

### 7.3 三步判断与精准匹配

```text
第一步：确定性程序
  外部流水号、金额、方向、日期时间、商户、摘要、来源和规范化指纹
  ├→ 证据充分：直接生成待用户确认的关系候选
  └→ 无法确定：进入第二步
第二步：职护现有 AI 的疑难关系建议
  只读取当前疑难项需要的最小脱敏证据，输出结构化建议和理由
  ↓
第三步：用户确认
  查看双方记录、证据和影响，选择关联、不关联、拆分或合并
```

程序能够确定时不调用 AI；AI 复用职护已有服务端配置，不新增供应商、模型配置或前端 Key。无论是否调用 AI，正式关系最终都必须由用户确认。

关系匹配等级由程序证据决定：

- **高**：稳定交易号一致，或存在唯一的一进一出记录且金额、币种、时间窗口和明确转账/结算语义全部闭合；
- **中**：金额、币种、方向和时间合理，但缺少共同交易号或仍有一项关键证据不足；
- **低**：只有同日同额、只有 AI 语义判断、存在多个等价候选或来源相互冲突。

关系等级与字段识别等级分别展示，AI 可以补充解释和候选关系，但不能自行把关系升级为高置信。

匹配结果必须展示：

- 建议是什么关系；
- 支持该关系的证据；
- 哪些字段一致；
- 哪些字段冲突；
- 如果确认，对收入、支出、净结余和报销状态有什么影响。

### 7.4 不增加“我的账户”确认

系统不建立单独的账户归属引导，也不要求用户先确认每张银行卡、微信零钱或支付宝账户是否属于本人。

因此，内部转账判断只能基于具体交易的双边流水、交易号、金额、时间、描述和上下文生成带证据等级的关系建议。证据不足时必须让用户在当前经济事实上确认“这是我的账户间转账”，不能声称已经自动精准判断。

用户对某一笔关系的确认只能作为相同来源模式、相同对方文本或同类关系的弱证据，不能悄悄升级成永久账户归属规则、自动提升为高置信，也不能跨用户、跨币种或跨不相关来源复用。

### 7.5 一对一、一对多、多对一和部分关系

必须支持：

- 一张工资条对应一次到账；
- 一张工资条分两次或多次到账；
- 工资和补贴合并为一次到账；
- 一笔聚合扣款拆成多个消费；
- 多笔消费合成一次公司报销；
- 一笔支出发生一次或多次部分退款；
- 一次转账在两个来源中各出现一端记录。

任何拆分或合并后，各部分金额之和必须通过程序校验；不平衡时保持待确认。

### 7.6 撤销、版本与重算

用户确认的操作都必须可撤销：

- 撤销一次批量入账；
- 将已确认记录退回候选；
- 修改分类或支出性质；
- 合并两端记录为转账；
- 解除错误匹配；
- 拆分混合消费；
- 将普通收入改为退款、报销或融资现金流；
- 恢复被错误排除的候选。

撤销后，程序重新计算受影响月份、分类、商户、预算、趋势和 AI 可用数据，不保留错误汇总。撤销正式事实后，未被其他事实占用的来源观察回到待核对或未分配状态；撤销一条多对多关系时只解除对应分配，不破坏同一观察上的其他合法分配。

来源观察保持不可变；修改经济事实、事实关系或分摊金额时，应产生新修订并把旧修订标记为 `superseded`，不能覆盖历史。当前账本维护递增的数据修订号。撤销或改账后，使相关 AI 缓存和分析快照失效。用户下载的历史导出和主动保存的 AI 分析不被后台悄悄改写，而是保留生成时间和账本修订号；账本变化后，界面明确标记旧结果“基于历史数据”，并提供重新生成入口。

“撤销”与“永久删除”是两种操作：撤销保留版本和最小审计且可恢复；用户主动删除识别批次、清空业务数据或删除账号时，按数据删除规则清除对应切片、OCR 原文、候选、事实和关系，不可恢复。

## 8. 统一可信账本与列表

正式列表只展示用户确认的经济事实和流水。至少支持：

- 月份和自定义日期范围；
- 全部、收入、支出、转账、退款、报销和融资现金流；
- 餐饮、出行、娱乐、住房、学习等分类；
- 固定、日常弹性、一次性、可报销等支出性质；
- 工资、奖金、兼职、副业、经营、投资等收入类型；
- 商户、交易对方、描述和金额区间；
- 来源类型和是否存在关联关系；
- 编辑、撤销、拆分、合并和查看证据。

列表中的每一笔至少能够打开“为什么这样记”的详情：

- 确认后的核心字段；
- 来源观察和 OCR 文字定位；
- 相关切图片段；
- 程序规则和 AI 建议；
- 重复、到账、退款、报销或转账关系；
- 用户确认、修正和撤销历史。

## 9. 图表、统计和守护分析

所有图表只使用已确认事实。候选即使金额完整，也不能参与图表、排行榜、预算、趋势或 AI 分析。

### 9.1 核心指标

- 本月已确认收入；
- 本月已确认支出；
- 本月净结余；
- 与上月相比的收入、支出和结余变化；

待处理批次数和候选数不属于顶部 KPI 或大图表指标。页面只在已确认列表之后提供一处轻量提醒入口，不汇总待确认金额，也不与正式统计并列。

### 9.2 大尺寸图表

- 每日、每周和跨月收支趋势；
- 本月与上月、去年同期对比；
- 收入来源和工资构成；
- 支出分类占比；
- 固定、日常弹性、一次性和可报销支出结构；
- 商户排行和高频交易；
- 周期性支出、订阅和固定账单；
- 工资应发、扣除、实发和实际到账趋势；
- 退款、报销和内部转账的独立口径；
- 预算使用进度、异常大额和月底预测。

### 9.3 统计真实性

- 退款冲减对应支出，不抬高收入；
- 报销与垫付支出关联展示，不伪装为劳动收入；
- 内部转账不影响收入、支出和净结余；
- 信用卡还款不重复计算已记录消费；
- 工资条本身不增加现金收入，实际到账确认后才进入账本；
- 缺少对比基线时显示“暂无可比数据”，不展示虚构的 `0%` 变化；
- 图表中的每个汇总数字都可以下钻到已确认记录。

## 10. AI 收支问询与建议

### 10.1 两类 AI 必须分开

| AI 类型 | 可以读取 | 不能做 |
| --- | --- | --- |
| 识别/导入 AI | 尚未确认但已脱敏的 OCR 文字、必要规范化字段和当前疑难候选 | 读取未脱敏 OCR 原文或图片切片、直接写入正式账本、自动确认 |
| 分析/问询 AI | 已确认经济事实、程序统计、用户已确认的工资/材料事实、相关知识 | 读取未确认候选并把它当成真实收支、自行算总额、直接改账 |

“只有确认数据才能进入 AI”特指收支分析、趋势建议和问询，不禁止识别 AI 使用尚未确认的 OCR 文字生成候选。

### 10.2 问询能力

用户可以询问：

- “这个月比上个月多花在哪里？”
- “餐饮支出最高的几家商户是什么？”
- “为什么这个月结余变少？”
- “工资为什么比上月少？”
- “这笔钱为什么被判断成退款，而不是收入？”
- “有哪些支出还没有报销？”
- “这两笔为什么被认为是内部转账？”
- “给我一些基于当前消费趋势的建议。”

回答必须：

- 使用程序预先计算的确定性指标；
- 标出数据范围和统计月份；
- 引用相关已确认流水、经济事实或工资项目；
- 区分事实、规则、知识和 AI 推测；
- 数据不足时明确说不知道，并告诉用户缺什么；
- 把可能修改账本的建议转成待确认操作，不能直接执行。

### 10.3 会话保存

AI 会话默认只服务于当前问询，不把完整对话作为正式财务事实。用户主动保存的分析结论可以形成独立记录，但必须引用当时的数据范围和统计快照；后续账本变化时提示结论可能已过期。

## 11. KNOWLEDGE：和当前问题相关的知识

收支守护页面必须包含场景化知识模块，而不是只跳转到通用知识学堂。

知识推荐至少覆盖：

- 工资结构、试用期工资、加班费、奖金和补贴；
- 社保、公积金、个税和专项附加扣除；
- 少发、多扣、迟发、漏发时的核对步骤；
- 消费分类、预算、固定支出和储蓄；
- 退款、报销、信用卡还款和内部转账口径；
- 与当前守护发现相关的材料清单和沟通方法。

收支守护首页的知识预览卡只展示阶段或分类、标题和摘要，保留文章详情入口及“查看全部知识 →”，不在卡片中堆叠“推荐依据”、来源、版本和审核状态。适用问题、适用地区、来源、内容版本、生效/失效时间、复核时间和 AI 可引用状态仍由后台完整维护，并在文章详情、知识治理和模型引用门禁中使用；过期内容必须下架或明确标记。知识用于解释通用规则，个人结论仍必须回到用户自己的已确认事实；不能用一篇通用文章直接认定用户的工资或权益存在问题，也不能基于未确认候选生成个性化结论。

## 12. 个人中心、导出和数据自主

收支守护数据与个人中心打通，至少支持：

- 按时间范围导出已确认收支流水；
- 按收入、支出、分类和来源筛选导出；
- 导出工资构成、到账匹配和守护发现；
- 导出 CSV、XLSX 和可读报告；
- 导出经济事实关系，例如退款对应哪笔支出；
- 所有默认导出只包含当前修订中已确认、未撤销的经济事实，并标明生成时间、时区和账本修订号；
- 查看和删除未完成识别批次；
- 删除识别切片、OCR 原文、候选和已确认结构化数据；
- 清空全部个人收支数据。

普通导出默认不包含整张原文件，因为系统不长期保存整张原文件。识别切片和 OCR 原文属于识别证据，不混入普通账本导出；如未来提供证据包导出，必须由用户单独选择。

普通账本导出的最低字段契约：

- 经济事实 ID、事件类型、当前确认状态和确认时间；
- 是否计收入、是否计支出；
- 金额、币种、分类、商户或对方、说明；
- 工资所属期间和实际到账时间；
- 来源证据数量、字段/关系置信说明和匹配理由；
- 退款、报销、工资结算或转账等关联事实 ID；
- 数据范围、时区、导出时间和账本修订号。

内部转账保留在明细中但明确标记“不计收支”；退款、报销不能导出为普通收入；`reversed`、`superseded` 和待确认数据默认不导出。CSV/XLSX 中的长交易号按文本导出，避免被转换为科学计数法。普通账本导出和包含切片/OCR 原文的证据包必须是两个独立动作。

## 13. 原文件、识别产物与隐私边界

### 13.1 保存范围

| 数据 | 是否保存 | 用途 |
| --- | --- | --- |
| 整张工资条/账单截图原文件 | 不长期保存 | 仅在本次预处理时使用，生成切片后删除 |
| 原始 CSV/TSV/XLSX 文件 | 不长期保存 | 解析为规范化行、字段映射和内容指纹后删除 |
| 原始 PDF | 不长期保存 | 转成页面或识别切片后删除 |
| 识别切图片段 | 可以保存 | 续办、字段定位、局部重试和证据查看 |
| 完整 OCR 原文 | 可以保存 | 重新结构化、证据定位和人工核对 |
| 规范化表格行 | 可以保存 | 字段映射、候选恢复和查重 |
| 结构化候选 | 保存至用户处理或删除 | 暂存退出和三档核对 |
| 已确认经济事实和流水 | 保存至用户删除 | 列表、图表、问询和导出 |
| AI 调用审计 | 保存最小元数据 | 功能点、模型、耗时、状态和错误码 |

### 13.2 生命周期

```text
接收原文件
  → 安全校验
  → 生成切片/OCR文字/规范化行/文件摘要
  → 删除整张原文件
  → 生成并保存候选
  → 用户确认或排除
  → 保存结构化事实和必要识别证据
  → 用户删除批次或清空数据时同步删除识别产物
```

原文件解析失败且未产生可续办数据时也应删除，用户重新选择后再试。不得因为实现方便继续依赖原始附件完成字段映射、批次恢复或重复判断。

默认留存行为：暂时关闭模态框时，识别切片、完整 OCR 原文、规范化行和候选随批次保留，便于下次继续；完成批次的识别产物继续随该批次保存，直至用户删除批次或清空数据。选择“删除本批次”时删除上述识别产物和未入账候选，但不自动删除已经确认的正式经济事实；删除正式事实需要单独操作。

### 13.3 安全与模型边界

- 识别切片、OCR 原文和规范化行都是用户私有敏感数据，必须鉴权隔离；
- 临时原文件使用用户隔离的临时目录和最小文件权限，不进入长期 uploads、对象存储或备份；
- 成功、校验失败、OCR 失败、AI 失败、超时和用户取消都必须在清理逻辑中删除临时原件，进程崩溃后由有界孤儿清理任务兜底；
- 反向代理、请求日志、异常追踪和错误报告不得另行保存原始请求体；
- 保存的连续切片按“可能重建敏感原件”的同等级别保护；
- 完整 OCR 原文不能写进通用应用日志或 AI 调用日志；
- 默认先在本地完成切图、OCR、脱敏和确定性解析；
- 启用腾讯云 OCR 且用户确认披露后，识别所需的派生切片会发送给腾讯云；整张原文件不长期保存，也不作为整图发送路径的默认实现；
- 职护现有识别/解释 AI 仍只接收任务所需的最小脱敏 OCR 文本或必要规范化字段，不接收未脱敏 OCR 原文和识别切片；
- 复用职护已有 AI 配置、服务端密钥和调用审计，不在前端新增厂商 Key；
- 用户删除批次、删除账号或清空业务数据时，识别切片、OCR 原文、候选、关系和正式流水必须按所有权精确清理。

## 14. 目标数据与服务契约

### 14.1 目标数据对象

目标模型至少需要表达：

- `RecognitionBatch`：一次工资条、文件、文字或 OCR 识别任务；
- `RecognitionArtifact`：切片、OCR 原文和规范化行；
- `TransactionCandidate`：待核对收支候选；
- `SalaryStatement`：工资所属月份和工资项目；
- `EconomicFact`：统一收入、支出、转账、退款、报销和融资事实；
- `LedgerEntry`：经济事实对现金账本的已确认影响；
- `ObservationFactAllocation`：来源观察与经济事实之间的多对多证据角色、分配金额和确认状态；
- `FactRelation`：经济事实之间的到账、拆分、合并、转账、退款、报销和替代关系；
- `GuardianFinding`：少发、多扣、重复、异常和待确认问题；
- `AnalysisSnapshot`：用户主动保存的分析范围和结果；
- `LedgerRevision`：正式事实和关系变化后的账本修订号，供 AI、导出和历史结果引用；
- `KnowledgeCitation`：守护发现或 AI 回答引用的知识来源。

具体表名可以沿用现有代码，但语义必须完整。不能继续用“一个候选只对应一条正式流水”的单一关系承载全部业务。

### 14.2 金额与统计

- 后端全程使用十进制定点金额，不使用二进制浮点数；
- 每个关系保存分配金额，拆分和合并必须守恒；
- 只有 `confirmed` 且未撤销的账本影响进入统计；
- 月份统计按真实发生/到账日期，工资分析另按工资所属月份；
- 所有写操作在确认时重新执行幂等、重复和关系校验；
- 前端重试不能造成重复入账。

### 14.3 AI 输出契约

AI 只输出受约束的结构化结果：

- 候选字段和字段置信说明；
- 疑难分类建议；
- 可能的事实关系和理由；
- 基于程序统计的解释；
- 需要用户确认的问题；
- 与当前问题相关的知识检索意图。

模型输出解析失败、超时或证据不足时保持候选状态，不能用默认值兜底写账。

## 15. UI、响应式和异常状态

### 15.1 视觉与层级

- 收入和支出两个入口面积、层级和交互权重相同；
- 不新增第二条页面导航；
- 主分析区使用大尺寸图表，不以大量小卡片把页面拉得过长；
- 绿色、黄色、红色只用于候选状态，不滥用于普通装饰；
- 已确认账本使用稳定中性的视觉，避免把正常消费全部表现为风险；
- KNOWLEDGE 保持现有职护的知识卡风格，并与当前问题建立明确关联。

### 15.2 桌面与手机

- 桌面双入口并排，手机上下堆叠；
- 图表在手机上切换为单列、可读的简化视图，不依赖横向宽表；
- 候选模态框在手机上使用全屏抽屉或全屏页面，底部确认操作始终可达；
- 长列表采用分页或虚拟滚动，不能一次渲染几千条；
- 所有筛选、编辑、确认和重复处理均可在触屏完成；
- 不出现页面级横向溢出。

### 15.3 加载、空态和错误

- 无已确认数据时显示“还没有已确认记录”，不展示四个伪造的零；
- 有候选无正式数据时，展示待处理提醒，不把它称为“没有记录”；
- AI 不可用时，文件解析、候选核对、账本和程序图表仍可用；
- OCR 某一片段失败时展示片段和重试入口，不让整个批次无解释消失；
- 写入成功但刷新失败时明确说明“记录已经成功，请刷新”，避免重复提交；
- 过期分析引用旧快照时展示数据更新时间和重新分析入口。

## 18. 验收标准

### 18.1 通用门禁

- 收入和支出两个入口在桌面和手机上平级；
- 页面内部没有第二套导航栏；
- 程序、OCR 和 AI 结果未经用户确认不进入正式账本；
- 未确认候选不进入列表、图表、预算、排行榜和分析问询；
- 缺失字段保持未知，不伪造 `0`；
- 所有确认、重复保留、合并、拆分和关系修改都可撤销并形成新修订；
- 每个候选展示置信层级和“为什么”；
- 每个正式汇总可以下钻到已确认事实。

### 18.2 收入守护

- 手工、CSV/TSV/XLSX、图片 OCR、截图和 PDF 均进入同一工资候选结构；
- 工资条自定义项目不丢失，空白字段不变成零；
- 可选择关联 Offer、合同、两者或暂不关联，并支持多材料版本；
- 未关联材料时仍有工资构成、扣款和跨月解释，但不作合同结论；
- 关联后可以展示 Offer—合同—工资条—实际到账的字段级差异；
- 工资所属月份与实际到账日期分开；
- 没有到账证据时只生成待确认到账候选；
- 工资条实发与到账不一致时，账本按实际到账，差额形成守护问题；
- 迟发、漏发结论必须有约定日期和到账证据。

### 18.3 支出守护

- 常见微信/支付宝长截图能够自动缩放、切片并完整生成候选；
- 不因文本截断或模型单次条数上限静默丢交易；
- 每个批次记录总片段数、成功/失败片段数、OCR 交易行数、去重前后候选数和跨片恢复数，并能定位未完成范围；
- 切片边界交易能够拼接，重叠区域能够去重；
- 绿色候选可选择后一键记录，黄色和红色必须逐项确认；
- 精确重复复用已有记录且不创建第二份来源观察；
- 疑似重复展示对应记录、匹配理由和取消/仍录入选项；
- 退出后可以从同一候选批次继续；
- 退款、报销、转账、信用卡还款和贷款本金使用正确口径。

### 18.4 经济事实与匹配

- 工资条、银行到账和钱包记录可以作为同一收入链的多份证据，不重复计算；
- 支持一对一、一对多、多对一和部分金额关系；
- 所有匹配先经过确定性程序；只有程序无法确定的疑难项才调用职护现有 AI；任何正式关系最终都由用户确认；
- 不增加“我的账户”维护或确认流程；
- 证据不足的内部转账只能提示用户确认，不能自动承诺准确；
- 退款和报销能够回到原支出并正确重算；
- 拆分和合并金额守恒。

### 18.5 图表、AI、知识和导出

- 图表覆盖趋势、月度对比、分类、商户、工资构成和特殊口径；
- 程序负责所有金额统计，AI 只解释程序结果；
- 识别 AI 只能读取未确认但已脱敏的 OCR 文字和必要规范化字段，分析 AI 只能读取已确认事实；
- AI 回答引用具体流水、工资项目和知识，并标明数据范围；
- KNOWLEDGE 根据当前工资或消费问题推荐相关知识；
- 个人中心可以导出已确认结构化数据、关系和报告；
- 默认导出只使用当前账本修订中的已确认、未撤销事实，并保存生成时间和修订号；
- 普通导出不包含不存在的整张原文件。

### 18.6 原文件与隐私

- 整张工资条、账单截图、CSV/TSV/XLSX/PDF 在生成必要识别产物后删除；
- 切图片段、完整 OCR 原文、规范化行和候选按用户隔离保存；
- 产品文案明确说明仍会保存切片和 OCR 文字；
- 完整 OCR 原文不进入通用日志或 AI 调用日志；
- 成功、各类失败、超时和用户取消场景均验证临时原件已清除，进程崩溃遗留由孤儿清理任务收敛；
- 原始请求体不进入反向代理日志、应用日志、异常追踪和长期备份；
- 用户删除批次或清空数据后，相关识别产物和结构化数据均被精确清理；
- 当前依赖原始附件的代码完成真实改造后，才可宣称“不保存整张原文件”。

## 19. 开发依赖顺序

以下只是工程依赖顺序，不是产品版本，也不代表后面的能力可以遗忘或移出范围：

```text
原文件生命周期与识别产物
  → 长截图分片 OCR 与三档候选
  → 统一经济事实和多关系模型
  → 工资条录入、材料核对与到账结算
  → 退款/报销/转账/信用卡等正确口径
  → 已确认账本的完整列表与大图表
  → AI 问询、场景化 KNOWLEDGE 和个人中心导出
  → 预算、固定收支、报告与月结
```

任何一步上线时，都必须继续遵守“候选先于账本、用户确认、程序算账、AI 解释、操作可撤销”的统一门禁。

## 20. 一句话产品定义

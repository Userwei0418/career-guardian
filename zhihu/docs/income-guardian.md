## 1. 产品定义

收支守护平等回答四个问题：

1. 这个月收入多少，分别来自哪里；
2. 这个月支出多少，主要花在哪里；
3. 已确认收入减已确认支出后，当前净结余是多少；
4. 哪些收入、支出、转账、工资扣款或导入结果仍需确认。

统一原则：

- 收入和支出在首页、导航、详情、统计和报告中平级；
- 工资核对是收入侧的专业能力，不等于全部收入；
- 收入、支出和转账共用一套用户私有流水底账；
- 转账不进入收入、支出和净结余，退款、报销和信用卡还款必须避免重复计算；
- 缺失数据保持未知，不用 `0`、演示数据或 AI 推断填补；
- 确定性程序负责金额、统计、查重和关联，AI 负责理解、候选和解释；
- 导入、OCR 和自然语言识别先生成候选，用户确认后才能写入正式流水。

## 2. 用户体验

首页第一屏平等显示本月收入、本月支出、本月净结余和待确认数量。没有已确认记录时显示“尚无已确认记录”或“暂无法计算”，不展示四个零；已经录入但仍待确认的记录也不能被误写成“尚未记录”。

```text
本月收入           本月支出
¥13,226            ¥7,480

本月净结余         待确认
¥5,746             5 笔
```

收入侧包含工资、奖金、兼职副业、经营收入、投资收益、报销、退款、补贴和其他收入；支出侧包含固定、日常弹性、一次性、可报销和其他支出。用户可以在统一流水中切换“全部、收入、支出、转账、待确认”。

月度状态只描述数据整理状态：尚未开始、整理中、存在待确认。系统没有用户月结确认和完整账户覆盖证据时，不自动声称“已经核清”。

## 4. 当前统一账本契约

当前代码新增：

- `financial_categories`：系统分类与用户自定义分类；
- `financial_transactions`：用户私有收入、支出和转账；
- `financial_import_batches`：文件、自然语言和 OCR 共用的用户私有导入批次；
- `financial_transaction_candidates`：正式入账前的逐行候选、校验、查重和用户修正；
- `personal_attachment_cleanup_jobs`：清空业务数据或删除账号后仍可重试的私有原件精确清理任务；
- `users.business_data_epoch`：阻止清空数据前已启动的长耗时导入、OCR 或 AI 请求在清空后重新写回候选；
- `/api/cashflow/categories`：分类列表与自定义分类新增；
- `/api/cashflow/transactions`：流水列表、新增、编辑和软删除；
- `/api/cashflow/summary`：按月确定性汇总；
- `/api/cashflow/imports`：文件上传、批次读取、字段映射、候选编辑和确认；
- `/api/cashflow/imports/text` 与 `/api/cashflow/imports/ocr`：复用同一候选入口的 AI 文本和本地 OCR 输入；
- `/api/auth/attachment-cleanups/{cleanup_id}/retry`：由原用户或管理员重试失败的精确附件清理任务。

流水至少保存：当前用户、方向、金额、币种、发生日期、分类、商户或来源、备注、支出性质、来源类型、来源引用、外部幂等键、确认状态和软删除时间。

收入和支出必须选择同方向的系统或本人分类；其他用户的自定义分类不可读取或引用。转账不能带收支分类，也不进入合计。只有 `confirmed` 流水参与收入、支出、分类和净结余；`pending` 与 `excluded` 分别统计数量但不改变金额。

金额在后端全程使用 `Decimal`，API 统一输出两位小数字符串；前端以十进制字符串和 `BigInt` 分为单位完成选择合计，不经过 JavaScript 浮点数。当前支持日期为 `1000-01-01` 至 `9998-12-31`，超出 MySQL 与月度边界的日期在候选或手工接口处明确拒绝。

## 5. 工资与现金流边界

工资条的实发金额是工资证据，不自动等于银行实际到账。工资链和现金流链必须分开：

```text
Offer/合同 → 应发 → 扣款 → 工资条实发

实际到账收入 + 其他已确认收入 - 已确认支出 = 本月净结余
```

未来关联工资到账时，应创建或关联一条真实收入流水，并使用来源引用避免重复录入。同一月份存在多份工资条时，不能简单相加为到账收入。

工资条当前仍需解决：可选项目空值在分析阶段被转为 `0`、详情/编辑/删除、可扩展工资项目、字段级来源、实际到账关联、跨月对比和月结状态。

## 6. 导入、OCR 与 AI

### 6.1 文件导入

导入统一采用：

```text
上传私有文件
→ 创建导入批次
→ 程序解析与格式校验
→ 外部键和内容哈希查重
→ 收入/支出/转账候选
→ 用户编辑、排除和确认
→ 幂等写入正式流水
→ 生成导入报告
```

当前代码已经增加 `financial_import_batches` 和 `financial_transaction_candidates`。同一用户、入口类型、来源、文件内容摘要和解析器版本共同约束批次复用；逐行候选保存安全业务字段、校验问题、警告、版本号、精确重复和疑似重复结果。正式流水继续使用 `(user_id, source_type, external_key)` 作为并发确认的最后一道唯一门禁。

文件读取边界为 10MB、5000 条和 80 列；Next 代理与最外层 ASGI 接收器都按实际到达字节数中止超限请求，不把 `Content-Length` 当作唯一门禁，文本、映射、候选编辑和确认 JSON 也有独立上限。支持 UTF-8 BOM、UTF-8、GB18030 的 CSV/TSV，以及不执行公式的首个 XLSX 工作表；解析器版本为 `cashflow-tabular-v3`。XLSX 限制 500 个压缩成员、32MB 总解压体积、工作表/共享文字/元数据体积、XML 节点数、文本节点数和 64 层深度，并严格读取 workbook、关系与 1900/1904 日期系统；元数据缺失、损坏或关系越界时拒绝文件，不猜测 `sheet1.xml`。旧 `.xls` 明确要求用户另存；通用表格字段不足时进入字段映射，不把第一条交易误当作表头。

精确重复默认不可导入，疑似重复必须由用户明确确认“不是同一笔”，只有 `ready` 候选可以写入正式账本。常见占位、掩码、短序号和低信息流水号不会成为跨文件硬身份；它们回退为文件行幂等，再交给疑似重复复核。疑似重复按方向、精确金额和日期形成粗桶，再比较确定性归一化后的商户/摘要；单桶精确扫描最多 100 条、一次预取最多 5000 条，超限时不伪装成“发现 1 条”，而是展示同日同金额记录数量，并把 `count + max_transaction_id` 水位绑定到用户接受证据。确认前水位或相似 ID 集合变化会强制重新核对。

确认按每批最多 500 条分段提交，前端串行衔接批次版本；后端以用户行锁串行化同一用户的手工增删改、导入确认和清空数据，再在确认事务中重新校验全部精确/疑似重复。即使两个文件使用不同外部键，并发提交相同疑似重复指纹，也只能有一笔进入正式流水，另一批回到显式复核。

日期型来源只保存交易日期，不虚构午夜发生时刻；即使原文件含精确时间，在当前界面尚不能让用户逐笔核对时，正式流水仍保守保存 `occurred_at = NULL`，候选中继续保留来源时间作为证据。当前正式账本仅支持 CNY；文件声明了币种列但某行为空、币种不支持、负数金额、收入/支出分列与显式方向冲突、非有限数值和超精度金额都会保持为阻断错误。源错误单独保留，只有用户显式修改对应事实字段才能解除，不能通过只改商户或备注绕过。

原文件是私有证据，不把账号、卡号、供应商流水号或带敏感标识的原始表头复制到候选/API。表头先转换为脱敏且唯一的公共列名，字段映射只在解析时以内存索引回到私有原件；样例值、商户、摘要和模型出站文字使用同一脱敏器。

### 6.2 OCR

票据、账单截图和长图先由服务端本机 Tesseract 做 OCR，再在本地脱敏连续或带空格/连字符的手机号、邮箱和长账号，仅将脱敏后的 OCR 文字交给职护当前文本模型做结构化候选解析。原图片不发送给模型；图片作为用户私有附件保存。图片在进入 OCR 前校验真实 PNG/JPEG/WebP 文件头，并从图片头读取宽高，拒绝超过 16000 像素单边或 2500 万像素的压缩炸弹。不得移植 OneBill 的智谱、腾讯 OCR、COS 或独立密钥配置。

OCR 候选保存模型、提示词版本、置信度、可在脱敏 OCR 文本中定位的短证据和候选状态。无法定位的模型证据会被丢弃并转成警告；所有 OCR 候选都必须由用户核对。当前未实现图片区域坐标，不能把文字证据写成版面级定位。

### 6.3 AI

自然语言记账、分类建议、月度解释和问答统一接入职护已有 AI 配置：

- 使用当前服务端供应商、模型能力和管理员配置；
- 复用现有 `AIInvocationLog`，功能点区分 `cashflow_text_parse`、`cashflow_vision_parse`、`cashflow_classify`、`cashflow_month_explain`；
- 不在前端新增厂商 Key，不把 OneBill 的模型配置复制进职护；
- 只发送当前问题所需的最小、可脱敏上下文；
- 金额合计、查重、预算和趋势由程序计算；
- 模型只返回结构化候选或对既有统计的解释；
- AI 失败时基础账本、导入预览和确定性统计仍可工作。

当前已实现 `cashflow_text_parse` 和 `cashflow_vision_parse`：配置读取和 `AIInvocationLog` 使用独立数据库会话，不会提前提交候选或正式流水事务；日志只记录功能点、模型、耗时、用量、状态和错误码，不记录输入正文。`cashflow_classify`、`cashflow_month_explain` 和收支问答仍待开发。

文件与数据库不能形成真正的单一原子事务。代码会在提交结果不明确时用新数据库会话按批次身份和附件 ID 复核，绝不删除可能已经被批次引用的原件；重传相同文件前会校验原件 SHA-256，缺失或损坏时以随机物理名原子修复。私有目录和文件分别使用 `0700` 与 `0600`，读取旧文件时失败即关闭并修复权限。清空业务数据或删除账号时，先在同一数据库事务写入带预期 SHA-256 的精确清理任务，提交后再删除物理文件；待处理任务优先于失败重试，成功后删除任务行，不永久保留用户/路径墓碑，失败任务则继续保留并可鉴权、幂等重试。后台孤儿扫描使用不跟随符号链接的有界续扫器，每轮最多处理 200 个文件、检查 1600 个目录项，并只查询本轮路径对应的附件和清理任务，不再全量物化私有目录树或两张路径表。

## 7. OneBill 参考边界

OneBill 已有账本、分类、预算、月度统计、微信 Excel 预览/查重/确认、文本记账、图片识别和消费问答。职护借鉴这些领域和交互，但不复用其 Java/Vue/H2/JWT、用户系统、厂商配置或运行服务。

OneBill 将部分提现、充值等中性交易转换为收入或支出参与统计；职护不采用这一口径。OneBill 的导入查重主要依赖应用内集合检查，职护需要持久化批次和数据库唯一约束。OneBill 会把较多交易级明文提供给模型，职护必须沿用现有隐私和调用审计边界。

## 8. 验收清单

收支守护完整验收至少覆盖：

- 收入与支出在桌面和手机上平级，不把支出藏成收入附属图表；
- 无数据、部分数据、待确认、排除和负结余状态；
- 金额两位小数与跨月边界；
- 转账不影响收入、支出和净结余；
- 分类方向匹配、系统分类可见、用户自定义分类隔离；
- 用户 A 无法读取、修改或删除用户 B 的分类和流水；
- 软删除不会出现在列表和汇总中；
- 重复导入、并发确认和失败重试保持幂等；
- OCR/AI 候选未经确认不进入正式账本；
- AI 无配置或调用失败时，基础账本和确定性统计仍可用；
- 工资条空白字段保持未知，工资条实发不冒充实际到账；
- 每个金额可以追溯来源、确认状态、导入批次和修改历史；
- 正式迁移、浏览器运行、真实 OCR/AI 调用和用户最终验收分别记录。

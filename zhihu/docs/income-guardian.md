# 收入与支出守护详细设计

- 文档版本：V0.1 开发前基线
- 更新日期：2026-08-21
- 文档状态：已按当前职护代码与 `/Users/zhouwei5/Downloads/OneBill` 参考项目完成开发前对齐；收入侧已有分散能力，支出侧尚未接入职护运行时
- 主入口：`/income`
- 现有工具：`/payslip`、`/salary`
- 参考项目：`OneBill`，只复用账本领域、导入确认和统计思路，不形成运行时依赖

## 0. 结论

收入守护下一阶段不再只是“工资条表单”或“税后工资计算器”，而是同一用户、同一月份下的收支事实闭环：

> 收入侧回答“钱从哪里来、为什么到手变化”；支出侧回答“钱去了哪里、哪些是长期负担”；最终只用可追溯事实计算本月结余，不用 AI 猜金额，也不要求用户先有 Offer、合同或完整账单。

本期仍属于五域中的“收入守护”，不新增第六个产品域。页面可以使用“收支守护”作为用户可理解的子标题，但后端职业事件类型继续使用 `income`，避免破坏既有五域契约。

## 1. 当前代码事实

### 1.1 已有能力

- `/income` 当前仍渲染通用 `GuardianOperationsWorkspace`，尚未形成专用月度收支首页。
- `/payslip` 支持手工录入工资月份、应发、实发、基本工资、绩效、补贴、社保、公积金、个税和其他扣除；Offer 关联可选。
- 工资条保存会写入 MySQL `payslips`、收入类 `CareerEvent`、`Evidence`、`GuardianFinding` 和必要的待办；接受 Offer 后的首薪待办可以回写同一事件。
- `/salary` 支持到手与生活结余试算、可选 Offer 回填、显式保存、列表、详情和删除；保存结果继续使用 MySQL `salary_calculations`。
- 薪资计算与工资条分析以确定性程序为主，模型不是金额计算器。

### 1.2 当前缺口

- 工资条只有固定列，没有可扩展的收入/扣款明细、字段来源、原文证据、用户确认状态和规则版本。
- 前端文案虽说明“空白是未知”，但实时分析和创建接口仍把部分空值转成 `0`；这会把“没填写”误写成“没有这项扣款”，必须优先修复。
- 工资条目前缺少独立详情、删除、核对状态、实际原因和跨月回看。
- `/income` 看不到“应发 → 扣款 → 实发”的资金路径，也没有真实的上月对比。
- 现有 `/finance` 是养老金、医保和公积金估算，不是消费账本，不能把它当成支出能力。
- 当前代码没有职护自有的账单、分类、预算、导入批次和月度支出统计模型。

## 2. 产品闭环

```text
工资条 / 手工收入 / 已保存薪资试算
                ↓
        本月收入事实与扣款核对
                ↓
手工支出 / 批量导入 / 用户确认分类
                ↓
      本月支出结构与固定负担核对
                ↓
到手收入 - 已确认支出 = 本月可解释结余
                ↓
用户标记：已核清 / 待补材料 / 暂无法解释
                ↓
              下月回看
```

收入和支出必须可以独立使用：没有工资条仍可记支出，没有完整支出也能核对工资；缺少的一侧显示“尚未记录”，不能补零。

## 3. `/income` 首页

首页控制为六个区域：

1. 本月结论：到手收入、已确认支出、可解释结余和当前核对状态；没有记录时展示起步空态，不展示四个零。
2. 收入资金路径：收入项目 → 应发 → 社保/公积金/个税/其他扣款 → 实发；未知项保持未知，算术不闭合时单独显示未解释差额。
3. 支出去向：固定支出、日常支出、一次性支出和转账/中性交易；每个数字可回到具体账单。
4. 先看这三件事：最多三条真正影响本月判断的问题，不制造大量告警。
5. 月度时间线：至少两个月后才显示真实变化，点击月份进入详情而不是重新填写。
6. 可选材料对照与知识：Offer、合同只在用户主动关联后参与；知识内容按当前问题召回。

首页主行动根据缺口变化：

- 没有收入：`核对一份工资条`；
- 没有支出：`记录本月支出`；
- 两侧都有但未闭合：`解释本月差额`；
- 已核清：`查看本月结论`。

## 4. 收入侧 P0

1. 修复未知值被当成 `0` 的真实性问题，前后端、数据库和分析结果统一使用 `null / unknown`。
2. 为工资条增加详情、删除、核对状态、用户确认原因和确认时间。
3. 用可扩展明细承载不同公司的收入和扣款项目，不再只依赖固定列。
4. 建立应发—扣款—实发资金路径与算术闭合检查。
5. 支持基于真实记录的上月对比。
6. Offer、合同保持可选；“材料没有写”与“存在冲突”分开。
7. 把已保存薪资试算作为摘要接入，不把实时试算冒充月度收入事实。

建议新增的收入明细至少记录：原始名称、标准分类、金额、收入/扣款方向、原文片段、来源类型、用户是否确认、是否参与应发/实发计算。

## 5. 支出侧 P0

首期只做可信的基础账本和月度结构，不先做复杂理财产品：

1. 手工新增、编辑、删除个人账单；每条账单必须归属当前用户。
2. 支持支出、收入和中性交易三种方向；转账、还款等中性交易不重复计入消费。
3. 分类支持系统默认和用户自定义；删除已使用分类时必须迁移或阻断，不能制造孤儿记录。
4. 支持按月份、分类、商户/备注筛选，并提供月度总额、每日趋势、分类占比和固定支出摘要。
5. 支持导入预览 → 校验/去重 → 用户确认 → 批量入账；识别结果不能直接写正式账本。
6. 预算是可选提醒，不是消费道德评分；预算超出只陈述事实和影响。

P0 不包含自动连接银行账户、自动抓取支付平台、替用户调整预算或自动删除交易。

## 6. OneBill 参考边界

`/Users/zhouwei5/Downloads/OneBill` 当前是一个尚无提交历史的独立参考项目：后端为 Java 21 / Spring Boot / MyBatis-Plus / Flyway，Web 为 Vue 3 / Vite / Pinia / Naive UI；职护为 FastAPI / SQLAlchemy / Alembic / Next.js。两者技术栈、认证和数据模型不同。

可复用的是：

- 账单、账单明细、分类、预算和统计的领域拆分；
- 手工记账、批量保存、筛选、月度汇总、分类占比和商户排行；
- 自然语言或图片识别先生成候选、用户确认后入账；
- 微信流水预览、校验、去重和确认导入；
- 结构化统计负责数字，模型只负责理解与解释；
- AI/OCR/对象存储未配置时，基础账本仍可工作。

不直接复用的是：

- OneBill 的用户表、JWT、登录页、品牌外壳和菜单；
- H2 开发运行时、Spring Controller、MyBatis Entity、Vue 页面和厂商密钥配置；
- 任何未经过职护所有权、MySQL 迁移、隐私和审计验证的 SQL 或接口；
- 文档中规划但尚未发布的 Maven/NPM 模块。

首轮实现应在职护仓库内按现有技术栈重写最小账本能力，而不是把 OneBill 启成第四个运行服务。

## 7. 数据与安全边界

- 正式运行只使用职护 MySQL；新增迁移先在名称含 `test` 的独立 MySQL schema 做升级、降级、旧数据和所有权回归。
- 金额使用定点数，明确币种和方向；时间保存完整时间与用户时区，月度汇总口径固定。
- 每个账单、分类、预算、导入批次和统计查询都必须带用户所有权条件。
- 原始流水文件私有保存；解析日志不记录完整账单、银行卡号、身份证、联系方式或模型 Prompt。
- AI/OCR 只处理必要、已脱敏内容；候选必须经用户确认后才能进入正式账本。
- 删除、批量导入和分类迁移保留可审计结果；不把日志当作正文历史库。

## 8. 开发顺序与验收

### 第一批：收入真实性

- 统一未知值语义；
- 工资条详情、删除和核对状态；
- 资金路径与跨月对比；
- 定向后端测试、前端类型/构建、桌面和手机浏览器验收。

### 第二批：支出基础账本

- 账单、分类、月度统计和所有权；
- 手工录入与编辑删除；
- 月度支出去向接入 `/income`。

### 第三批：导入与预算

- 微信流水或通用表格的预览、去重、确认导入；
- 可选预算和固定支出识别；
- 再评估图片识别和消费助手，不提前承诺外部厂商能力。

完成标准不是页面存在，而是至少覆盖：用户隔离、未知值、金额精度、中性交易、重复导入、删除边界、月度汇总一致性、手机布局和服务端错误状态。

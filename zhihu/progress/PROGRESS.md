## 0. 当前紧急任务结果与生产前边界

2026-08-18 已确认根因不只是“列表选择器失效”，而是采集链路缺少对入口有效性、详情导航、完整渲染 HTML、详情正文和失败事实的统一管理。本轮已完成：

1. 列表岗位只是发现索引。适配器现在会打开独立详情页、从卡片 ID 构造受限同域详情 URL，或在没有 href 时按可见标题点击。它保留完整渲染 HTML、可读正文、抓取模式、命中选择器、导航策略和警告，然后再进入程序标准化、按需 AI 语义拆分和质量门。
2. 任务不再把“页面打开但没有详情”写成成功。失败现在区分 `source_entry_invalid`、`list_parse_failed`、`detail_navigation_failed`和 `detail_content_failed`；零详情证据的批次直接失败，空职责/要求记录不会被质量门放行。
3. 58 同城旧入口 `https://campus.58.com/campus/jobs` 已 404，目录已改为新的 `campus-recruitment` / `social-recruitment` hash 路由，用 `#/job/` 语义链接识别详情。入口 404 不会由 AI 猜测一个新 URL；系统会记录入口失效并要求管理员核对新入口。
4. 健合 HotJob 卡片不再当成完整岗位；兼容解析器提取 `postId`，声明式同域模板打开 `posDetail.html?postId=...&postType=society`后抓正文。
5. 管理员任务详情会显示 Raw HTML 字符/字节数、正文长度、抓取模式、详情策略、命中选择器和警告；完整 HTML/正文只能由管理员按需打开，HTML 在 `<pre>` 中转义显示，不执行脚本或 iframe。任务时间线可展开 JSON 上下文；失败日志保留错误类型、类别、消息和恢复建议。
6. AI 调用明细保留调用时间、主体、能力类型、页面/功能点、供应商/模型、状态、耗时、用量、成本和错误类型；“采集解析规则自动修复”使用系统主体。不保存 Prompt、页面完整 DOM、简历、Offer、JD 或模型回复正文。
7. 参考 `qzclawler` 后已将公开学校配置和安全兼容解析器包装为职护自有资产：308 个学校配置、667 个公告来源、85 个解析器。学校公告已接入与企业渠道相同的 Raw、标准化、质量门和 Core 岗位主库；导入不会批量启用来源，且只有能取得明确招聘单位和完整岗位事实的记录才晋级，不确定记录继续隔离。
8. 原爬虫逐详情使用 3～10 秒随机间隔。职护现已恢复来源级节奏，并允许管理员在每次采集前填写随机等待最小/最大秒数。单次覆盖写入 `crawl_tasks.run_options`，不会污染渠道默认配置；渠道最小请求间隔仍是不可被单次任务降低的安全下限。`collection_snapshot` 日志记录配置范围、实际等待次数和累计等待毫秒数；页面渲染等待与请求节奏分开记录。
9. 管理员在每次采集前可选择渠道默认/无头/可见浏览器、渠道默认/全量/增量、最大页数、最大记录数和随机等待范围。运行时把请求值、生效值、分页动作、加载批次、停止原因和详情完成度统一保存在任务及事件日志中。
10. 站点明确显示“暂无职位”等空状态时，任务记为成功的零结果并写 `source_empty_confirmed`，不会误报解析规则失效，也不会生成无意义的 AI 修复候选。
11. `DataError / Data too long for column / raw_records` 被归类为 `storage_schema`，恢复动作是检查 MySQL 迁移，不再增加解析策略失败次数或错误触发 AI 规则修复。
12. 管理后台已改为可收起的左侧导航；企业渠道与学校公告共用卡片层级、来源状态筛选和采集任务区。筛选项包括全部、已启用、待启用、被弃用、待审查（有问题）。
13. 采集弹窗会直接显示来源默认最大页数、最大记录数和详情随机等待范围。管理员可终止排队或运行中的任务；操作使用站内二次确认，不再弹浏览器原生 `confirm`。请求人与原因写入 `task_cancel_requested`，执行器在页面等待、翻页、详情等待和逐条存储边界响应后写 `task_cancelled`，已经写入 Raw 的记录不会因主动终止回滚。
14. 管理后台左侧导航在桌面端固定于视口，不随内容滚动；公司和学校的来源状态筛选均收进各自列表标题栏下拉框。公司与学校行内的状态操作统一为单一下拉框“启用 / 暂停 / 弃用”，弃用仍经站内二次确认并以 MySQL 治理状态持久化，不删除渠道配置、Raw、岗位主库或审计历史，可由管理员重新启用。
15. 学校来源卡片标题使用单行截断并保留原文悬停提示，长校名不会再挤压来源状态、健康状态和采集操作区。
16. 管理后台新增公司管理和职位管理：使用正式 MySQL 的 Core 公司/岗位主库，支持新增、查看、编辑、软删除、搜索、状态筛选、排序、服务端分页和每页条数选择；职位手工发布仍受正文完整性约束。
17. 公司/职位 CRUD 均写入独立管理员审计表，保留实体、动作、操作者、变更前后快照和时间。职位删除会明确记录为“删除”，旧版曾把软删除记成“编辑”的历史事件也会按状态变化正确显示；页面展示实体名称、状态变化、记录编号和操作者。
18. 管理导航按业务归属调整为“数据采集 → 数据准入 → 审查规则”，审查规则位于第三个数据治理模块之下；展开侧栏时职位筛选区恢复紧凑单行布局，缩小控件高度、间距和列宽，不再出现大块两行表单或竖排按钮。

## 1. 产品目标

职护面向应届生和入职 0～3 年的职场新人，围绕五个守护领域提供连续帮助：

| 守护领域 | 用户真实问题 | 产品结果 |
| --- | --- | --- |
| 机会守护 | 岗位真实吗、适合我吗、市场情况如何 | 市场全景、岗位事实、匹配差距、目标与训练 |
| 决策守护 | 外部拿到的 Offer 值不值得去、两份怎么选 | 收入拆解、市场位置、城市成本、条件化建议 |
| 权益守护 | 合同、试用期、竞业、加班有没有坑 | 条款解释、规则依据、承诺差异、确认话术 |
| 收入守护 | 工资为什么变少、社保公积金对不对 | 工资条核对、扣款解释、材料一致性 |
| 成长守护 | 入职后学什么、何时跳槽、能力差在哪里 | 能力路线、阶段任务、训练记录、机会变化 |

职护不参与真实招聘和真实投递；岗位用于市场认知、目标设定、简历准备和模拟训练。决策守护分析用户从外部渠道获得并主动录入的 Offer，不由岗位收藏自动生成 Offer。

## 2. 当前运行架构

```text
浏览器 Web（Next.js，默认 3000）
├── 职护业务 API（FastAPI，默认 8000）
│   ├── 用户、简历、目标岗位、AI 分析、模拟面试、五域业务
│   └── 管理员 AI 配置与统一调用日志
└── 市场数据服务（FastAPI，默认 8100）
    ├── 公司与招聘渠道、Playwright 采集任务
    ├── Raw 留痕、标准化、去重、语义清洗、质量门
    └── Core 岗位、市场洞察、解析策略版本与恢复流程
```

生产与本地业务运行统一使用 MySQL：

- `zhihu`：产品主库；用户、简历、文章、清洗后的岗位、企业、城市、技能、守护记录、AI 结果等均在此库。
- `market_raw`：渠道、采集任务、原始岗位、处理轨迹、策略版本、恢复候选等采集治理数据。
- `pin_legacy_staging`：历史迁移与审计证据，只作隔离来源。
- MySQL 是唯一受支持的开发、验收与运行数据库。现有历史单元测试夹具不构成运行或正式验收证据。
- `Pin`：历史参考项目，职护运行时不得读取其代码、配置、数据库或服务。

数据库和字段以迁移与运行代码为最高事实来源，动态数量必须查询当前接口或数据库。`132,804` 只是历史迁移基线，不应作为页面或文档中的固定总数。

## 3. 已实现的稳定能力

### 3.1 机会守护

- 市场全景先于求职方向，包含岗位、企业、城市、职类和招聘类型图表。
- 支持预设方向和自定义专业/方向，进入方向后展示需求技能、学历结构、读研参考、城市与岗位结构等分析。
- 岗位列表支持智能推荐与全部岗位、组合搜索、每页数量、分页和排序。
- 推荐使用召回、重排和统一证据评分，不只统计技能词，也考虑职务、方向、专业、城市、招聘类型、工作经验/背景门槛、岗位完整度与简历证据。
- 岗位详情支持指定简历分析、收藏、设为目标；匹配分由统一规则维护，AI 解释证据，不自行改分。
- 目标岗位支持能力路线、简历微调、并排同步滚动差异查看和新简历版本确认保存。
- 目标岗位支持端到端实时语音模拟面试；保存逐字稿、固定维度评分、复盘与摘要，不保存面试语音。
- 个人中心包含收藏与目标、简历版本、面试成长、专项练习与固定话术沉淀。成长趋势可按近期或全部有效场次观察。
- 能力路线摘要朗读音频按“摘要 + TTS 模型 + 音色 + 语速等参数”计算缓存哈希，避免重复生成。

### 3.2 招聘数据采集与质量治理

- 职护自有公司、招聘渠道和平台模板；每家公司可维护校招、实习、社招等多个渠道。
- 单次任务可选渠道默认/后台无头/可见浏览器、渠道默认/全量/增量、最大页数、最大记录数及随机等待最小/最大秒数；任务保存请求参数、生效参数和实际运行证据。
- 管理员可通过站内二次确认终止排队或运行任务；任务状态和请求人、原因、最终收敛结果可审计，已经写入 Raw 的内容保留。
- 支持下一页、加载更多、无限滚动和声明式详情展开/详情页抓取；加载策略、边界与实际动作进入任务证据。
- 支持按渠道检查点做增量采集，并定期全量回扫；不能只依靠页码或同标题判断增量。
- 数据经过完整 HTML/正文 Raw 留痕、程序标准化、内容哈希/身份去重、按需 LLM 语义兜底和版本化质量门后才可进入 `zhihu.market_jobs`。程序提取充分时不调用 LLM；程序提取不充分且存在来源正文时调用 LLM，结果仍需逐字证据校验和质量门。
- 缺失职责、任职要求或足够 JD 正文的岗位不得晋级 Core；应先判断页面是否需要展开或进入详情，再决定重抓或隔离。
- 管理员可查看公司/渠道状态、采集任务、任务新增内容、处理轨迹、隔离原因、策略版本、回放、审批和回滚。
- 解析规则恢复采用声明式候选，不允许 AI 直接写入或执行任意 JavaScript/Python；候选须经过受限回放、Canary、人工审批，生效版本可回滚。

权威链路文档：[`recruitment-collection-pipeline.md`](../docs/data/recruitment-collection-pipeline.md)。

### 3.3 决策守护

- 入口面向“我已经从外部拿到 Offer”，支持手工录入或材料解析。
- 支持薪酬结构、真实收入、城市成本、市场位置、风险待确认项和个人偏好权衡。
- 支持多 Offer 比较、HR 确认话术、谈薪准备、最终决定历史。
- 接受 Offer 后可以把已确认事实流转到权益、收入和成长守护；不与机会守护中的岗位收藏伪造关联。

当前业务边界：[`decision-guardian.md`](../docs/decision-guardian.md)。

## 5. 已完成的采集规则 AI 自愈闭环

本节保留已验收要求，供以后回归；不再是“待完成紧急任务”。

### 5.1 功能验收

1. 新的解析规则失效任务自动产生一条与失败任务、公司、渠道、故障签名关联的修复候选。
2. 管理员页面能看到：待 AI 生成、生成中、候选已生成、回放失败、Canary 通过、已批准、已回滚、生成失败。
3. 候选只含允许字段和有限参数；任何代码、凭证、Cookie、请求头或跨域 URL 均被拒绝。
4. AI 生成后不直接生效；管理员可查看证据和差异，执行受限回放，通过后审批，小范围验证，异常可回滚。
5. AI 不可用或生成失败时，采集任务保持失败/隔离事实，不伪装成功；管理员可人工编辑声明式候选。
6. 同一失败签名不会无限生成重复候选；重复故障复用或更新现有候选。
7. Worker 异常退出后任务可恢复，`ai_generating` 有租约/超时回收和有限重试。

### 5.2 AI 调用审计验收

- 调用用途/功能点显示“采集解析规则自动修复”。
- 记录系统主体或触发管理员、触发页面、时间、供应商/模型、模态类型（文本）、成功失败、耗时、输入/输出 Token 和可得成本。
- 不记录完整页面 DOM、Prompt、JD 原文、密钥或模型完整响应。
- 后台统计能计入总调用、结果构成、能力类型和用量汇总。

### 5.3 数据质量验收

- 用至少一个真实可访问渠道制造或复现解析失败。
- 新候选回放出的代表岗位必须与官网“展开后/详情页”逐项比较标题、城市、发布时间、职责、任职要求和来源 URL。
- 职责、要求或足够 JD 正文缺失的记录不得晋级 Core。
- 任务详情必须能解释每条数据为何晋级、隔离或重复。

### 5.4 浏览器模式验收

- 选择“本次全部使用可见浏览器”后，真实 Playwright 进程应以可见模式运行，并在任务事件中记录 `requested=visible`、`actual=visible`。
- 若运行环境无法显示窗口，任务必须明确失败或降级说明，不能静默改成无头后仍声称可见。
- 后台无头和可见模式必须复用同一解析、增量、Raw、质量门和 Core 链路，差异只在浏览器呈现与少量风控特征。
